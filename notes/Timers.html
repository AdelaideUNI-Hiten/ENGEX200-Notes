Refresh the basics first

Timers lean hard on ideas from earlier lectures — registers, bits, pointers, interrupts. If any of these feel shaky, open them up. If you're confident, skip straight to Section 01.

What actually is a register?

A microcontroller chip is packed with tiny circuits called peripherals — GPIO pins, timers, communication ports, and so on. Each peripheral is controlled by a handful of numbered memory slots called registers. A register is just a box that holds a fixed number of bits (usually 32 on these chips), sitting at a specific, fixed memory address.

Writing a number into a register changes the peripheral's behaviour instantly — in hardware, not software. Reading a register tells you the peripheral's current state. In C, we don't normally type raw addresses; instead the toolchain gives us named "shortcuts" like TIM16->PSC, which behind the scenes points straight at the correct memory address for that register.

Binary & hex, fast

Registers are just numbers, but we usually think about them bit by bit (each bit is a 0 or 1, and a specific bit often means a specific thing — "counter enabled", "interrupt pending"). Two number systems show up constantly in this chapter:

FormExampleValue
Binary0b00010001bit 0 and bit 4 are set → decimal 17
Hex0x11same value, decimal 17
Decimal17same value

Hex is popular because each hex digit maps to exactly 4 bits, so 0x80 (used later for debouncing) is instantly "bit 7 is 1, everything else is 0" — 0b10000000.

Bitwise operators cheat sheet

You will see the same handful of patterns in almost every line of register code this chapter. Learn these five and the rest of the syntax stops being scary:

PatternReads asUsed for
reg |= (1<<n)"set bit n to 1, leave everything else alone"enabling a clock, enabling an interrupt
reg &= ~(1<<n)"clear bit n to 0, leave everything else alone"clearing an interrupt flag
reg ^= (1<<n)"flip bit n — 0 becomes 1, 1 becomes 0"toggling an LED
reg & (1<<n)"is bit n currently 1?" (reads without changing)checking if a flag fired
reg = value"overwrite the whole register with this number"setting PSC, ARR to an exact count

1<<n just means "take the number 1 and shift it left n places", which produces a number that is all zeros except a single 1 sitting at position n. It's the standard way to point at "just this one bit" without typing it out in binary.

Why the arrow, TIM16->PSC?

TIM16 is a pointer to a C struct that lays out every register belonging to Timer 16, in the exact order they exist in memory (CR1, then DIER, then SR, then CNT, PSC, ARR...). Because TIM16 is a pointer, we use -> instead of . to reach inside it. So TIM16->PSC = 47; means "go to Timer 16's block of memory, find the PSC slot inside it, and write 47 there." This is exactly the same struct-of-registers pattern you used for GPIOA-> in the Memory/Registers/GPIO lecture.

What does volatile mean, and why does it matter here?

Normally, the compiler is allowed to optimise your code aggressively — including deciding "this variable never seems to change from the code I can see, I'll just cache it once." That's a disaster for a variable that a hardware peripheral or an interrupt can change behind the compiler's back (like a timer's counter, or a flag flipped inside an ISR). volatile tells the compiler "don't assume — always re-read this from memory, every single time." You'll see it on hardware registers and on any flag variable that's shared between an interrupt and main(), e.g. volatile uint8_t is_blinking later in this chapter.

Interrupts & the NVIC — quick recap from Lecture 3

An interrupt lets a peripheral pause whatever the CPU is doing and force it to jump to a special function immediately — no need for the CPU to keep asking "has anything happened yet?" (that constant asking is called polling, and it wastes CPU time).

The NVIC (Nested Vectored Interrupt Controller) is the traffic controller sitting between all the chip's peripherals and the CPU core. Each peripheral has its own interrupt line; NVIC_EnableIRQ(SomeName_IRQn) tells the NVIC "let this peripheral's interrupts through." When one fires, the CPU jumps to a specific function called the ISR (Interrupt Service Routine) — for Timer 16, that function is always named TIM16_IRQHandler, a fixed name the startup code already knows to jump to.

This chapter reuses exactly this pattern for timers, and later combines it with the EXTI (external interrupt) pins you met in Lecture 3.

01 · WHY TIMERS EXIST

The microwave problem

Press power, set 10 seconds, hit start. How does the microcontroller inside know exactly when 10 seconds are up — down to the millisecond — while also watching the door sensor in case you open it early?

The obvious first idea: write a loop that counts. Something like this:

volatile bool cooking = true;
uint32_t cook_time_cycles;

void run_microwave(uint32_t cook_time) {
  while (cooking) {
    // clock runs at 48 MHz → 1 second = 48,000,000 cycles
    cook_time_cycles = 48000000U * cook_time;
    delay(cook_time_cycles);

    if (door_is_open()) { stop_cooking(); }
  }
}

static void delay(volatile uint32_t count) {
  while (count > 0U) { __NOP(); count--; }
}

This is a software delay loop: the CPU just sits there, burning through millions of do-nothing instructions, counting down. It's simple — and it has a serious flaw. Try it below.

Try it — blocking software delay

Click Start cooking, then immediately try clicking Open door while it's running. Warning: this really will freeze this page for a moment on purpose — that's the point.

Notice the door button simply didn't respond while the delay loop was spinning — because nothing else can run while the CPU is stuck inside that while loop, including checking the door sensor. Now try the fixed version, which hands the waiting off to a piece of hardware and lets the CPU stay free:

The takeaway A software delay loop makes the CPU unavailable for the entire wait — it can't check a door sensor, update a display, or respond to a button. The fix is to hand the waiting job to a piece of dedicated hardware that counts independently, and have it interrupt the CPU only at the exact moment it's needed. That dedicated hardware is a timer.
01 · WHY TIMERS EXIST

What is a hardware timer?

A hardware timer is an independent peripheral built into the chip that counts — clock cycles, or pulses arriving from outside — entirely on its own, without the CPU (the Cortex processor core) lifting a finger.

Think of it exactly like setting an alarm clock before a nap: you set the alarm (configure the timer), you go to sleep or do other work (the CPU carries on running your program), and the alarm clock itself keeps time in the background, waking you up (firing an interrupt) the instant the set time is reached. You never had to keep glancing at a clock yourself.

Core idea Set an alarm for the CPU → let the CPU do other work → a hardware interrupt notifies it exactly when time is up. This is the opposite of the microwave's software loop, where the CPU itself had to do the counting.

Once you have a piece of hardware that can count independently, it turns out to be useful for a lot more than just delays:

⏱ Precise time bases & delays

Generate an event every exact millisecond, second, or any interval you calculate — accurate to a single clock cycle.

⚡ Triggering hardware interrupts

Notify the CPU the instant the counter reaches a target, so it can react without ever having to ask.

📶 Counting external pulses

Count real-world events arriving on a pin — e.g. pulses from a rotary encoder or a speed sensor.

🌊 Generating PWM signals

Produce repeating on/off square-wave signals used to drive motors, dim LEDs, or control servos.

01 · WHY TIMERS EXIST

Not all timers are the same

A real microcontroller usually has several timer peripherals on board, split into three families of increasing capability. Which ones — and how many — you get depends entirely on the specific chip.

Basic Timers

Not connected to any GPIO pins — they can only count. Used for internal jobs like periodic interrupts or a system "tick" (a background heartbeat other code can rely on).

General Purpose Timers

A counter plus one or more Capture/Compare (CapCom) channels wired to actual GPIO pins. This lets them generate output signals (PWM / square waves) or capture input signals (e.g. pulses from an external sensor).

  • Single-channel — perfect for switch debouncing and simple time bases. This is the type used throughout this chapter (TIM16).
  • Multi-channel — generating several PWM signals at once, or reading rotary encoders.

Advanced Control Timers

A CapCom timer plus specialised safety and switching hardware built for handling real power. Used to drive brushless DC motors (via an H-Bridge), switch-mode power supplies, and inverters.

01 · WHY TIMERS EXIST

Every timer boils down to three registers

However complicated a timer peripheral looks in the reference manual, its basic ticking behaviour is controlled by just three registers. Learn these three and the rest of the chapter is mostly plumbing.

CNT
Counter Register

Holds the current count value. An n-bit counter ranges from 0 to 2ⁿ−1 — TIM16 is 16-bit, so CNT runs from 0 to 65535 before it would naturally overflow.

PSC
Prescaler Register

The chip's internal clock ticks in the tens of millions of times per second — far too fast to count anything human-scale directly. PSC divides that clock speed down to something usable.

ARR
Auto-Reload Register

Sets the upper limit for CNT. Once CNT == ARR, an update event fires (which can raise an interrupt flag) and CNT automatically resets to 0.

Picture it like an odometer that's only allowed to count up to a chosen number before flipping back to zero and ringing a bell each time it does — that bell is the update event you'll hook an interrupt onto in Section 02.

01 · WHY TIMERS EXIST

Timer maths

Four formulas connect the numbers you choose (PSC, ARR) to the real-world timing you actually want. They all fall out of one idea: the clock gets divided twice — once by the prescaler, once by the auto-reload.

Zero-indexed registers Both PSC and ARR count from 0, so a register value of 0 means "divide by 1" / "1 total count", not "divide by 0". That's why every formula below has a + 1.

Timer frequency, ftimScaled-down version of the chip's clockf_tim = f_clk / (PSC+1)

Update period, TupdateTime between reset events (CNT: 0→ARR is ARR+1 ticks)T_update = T_tick × (ARR+1)
Update frequency, fupdateHow often the reset/interrupt event happensf_update = f_clk / ((PSC+1)(ARR+1))

Quick targets (auto-solves PSC/ARR for f_clk = 48 MHz):

Worked example, step by step

Goal: trigger an update-event interrupt at exactly fupdate = 1 kHz, given the chip's clock is fclk = 48 MHz.

Write down what you need

(PSC+1)(ARR+1) = f_clk / f_update = 48,000,000 / 1,000 = 48,000

One equation, two unknowns — so there isn't a single correct answer. We need a sensible rule to split 48,000 into two factors.

Rule of thumb: scale the clock to 1 MHz first

PSC+1 = f_clk / f_tim = 48,000,000 / 1,000,000 = 48 → PSC = 47

Choosing ftim = 1 MHz means every tick is a clean 1 microsecond — easy to reason about, and it leaves plenty of headroom in ARR (16-bit, so up to 65,536 counts) for a wide range of target frequencies.

Solve for ARR

ARR+1 = 48,000 / (PSC+1) = 48,000 / 48 = 1,000 → ARR = 999

Done

Set PSC = 47 and ARR = 999. Try it in the calculator above — click "Load the slide 10 example" to see it land exactly on 1 kHz.

02 · TIMER REGISTERS

Setting up a timer, step by step

Every peripheral on the chip lives somewhere in the chip's memory map — a giant address book that tells the processor exactly where to find each peripheral's registers (RM0490, Table 7, pages 49–51). We'll set up TIM16 as our working example; every other timer follows an identical procedure with a different name and address.

Turn the peripheral's clock on

Peripherals don't run for free — to save power, most of the chip's peripherals have their clock switched off by default. Timers sit on the APB bus, so we flip the matching bit in the RCC (Reset and Clock Control) peripheral before touching anything else. Bit 17 of APBENR2 specifically enables TIM16 (RM0490, Table 31, p.164).

RCC->APBENR2 |= 1<<17; // Enable clock for TIM16

Choose the tick rate — write PSC and ARR

Unlike a lot of registers where you set individual bits, PSC and ARR are registers you simply write a whole number into — the value you write becomes the value used by the counter. Using the worked example above (fupdate = 1 kHz at 48 MHz):

// Set timer to have update rate of 1 kHz
TIM16->PSC = 47;   // Prescaler → scales clock to 1 MHz
TIM16->ARR = 999;  // Auto-reload → 1000 ticks per update

TIMx_ARR — bits [15:0] hold the 16-bit reload value (RM0490, Table 95, p.629). PSC has the same 16-bit layout.

Enable the counter itself

So far the timer is configured but not actually running. Bit 0 of the control register CR1 is the counter-enable (CEN) bit — flipping it starts CNT counting.

TIM16->CR1 |= 1 << 0; // Enable counter
Order matters (a little) Configure PSC and ARR before enabling the counter (CR1) — otherwise the timer might start counting for a moment with old or default values before your settings take effect.
02 · TIMER REGISTERS

Events & interrupt flags

We've never actually touched the CNT register — so how do we find out when it reaches ARR? Two options.

✗ Polling 
if(TIM16->CNT == TIM16->ARR){
  // do something
}

Works, but the CPU has to keep asking, over and over, wasting cycles it could spend elsewhere — the exact same wastefulness as the microwave's software delay loop.

✓ Interrupts

Enable the timer's update interrupt so the hardware notifies the CPU automatically the instant CNT reaches ARR. The CPU is free until that exact moment.

Enabling this is one bit, in the DIER register (DMA/Interrupt Enable Register) — specifically the UIE bit (Update Interrupt Enable), bit 0:

TIM16->DIER |= 1 << 0; // UIE — enable the update interrupt

This alone doesn't run any of your code yet — it just tells the timer peripheral "when you reach ARR, please raise your interrupt line." Two more things are needed, covered over the next two sections: telling the NVIC to actually pass that signal through to the CPU, and writing the function that runs when it does.

02 · TIMER REGISTERS

Writing the interrupt handler

Every peripheral capable of interrupting has its own dedicated ISR function name and its own line into the NVIC (RM0490, Table 56, p.260). For TIM16 that name is fixed: TIM16_IRQHandler.

Putting the whole chain together — clock on, timing configured, interrupt enabled, NVIC told to listen, counter started:

RCC->APBENR2 |= 1<<17;        // 1. Enable clock for TIM16
TIM16->PSC = 47;              // 2. Scale clock to 1 MHz
TIM16->ARR = 999;             // 2. 1000 ticks per update → 1 kHz
TIM16->DIER |= 1 << 0;         // 3. Enable TIM16's update interrupt (UIE)
NVIC_EnableIRQ(TIM16_IRQn);   // 4. Let the NVIC pass it through to the CPU
TIM16->CR1 |= 1 << 0;          // 5. Enable the counter — go!

void TIM16_IRQHandler(void){
  // runs automatically, the instant CNT reaches ARR
}

Inside the handler, one more register matters: SR, the status register. Bit 0 is the UIF flag (Update Interrupt Flag) — it gets set by hardware the moment the interrupt fires, and it's how your code confirms why it's here (a timer might have several different interrupt sources sharing one handler in more advanced setups).

void TIM16_IRQHandler(void) {
  if (TIM16->SR & (1<<0)) {          // Did the update flag actually trigger?
    TIM16->SR &= ~(1<<0);        // Clear it, ready for next time
    GPIOA->ODR ^= (1<<5);         // Do the actual work — toggle LED on PA5
  }
}
The #1 timer bug Forgetting to clear the flag (TIM16->SR &= ~(1<<0);) means the CPU thinks the interrupt is still pending the instant it exits the handler, and immediately re-enters it — usually locking your program into that ISR forever. Always clear the flag you just handled.

Example 1 — Blinking an LED at exactly 1 kHz

Same LED-blink task from Practical 2, but this time we're not guessing at loop iterations — we're specifying the actual real-world period, using everything from Section 02.

Every program in this course follows the same overall skeleton:

#include "stm32c0xx.h"

void SystemInit(void){
  // STM32 startup routine — leave empty, startup.s handles this
}
void RegisterInit(void){
  // All register / interrupt setup goes here
}
void Peripheral_IRQHandler(void){
  // Runs automatically when that peripheral interrupts
}
int main(void){
  RegisterInit();
  while(1){ /* do something, or nothing at all */ }
}

Filled in for the blinking LED (PA5), driven by TIM16 at 1 kHz:

void RegisterInit(void){
  RCC->IOPENR  |= 1<<0;   // Enable clock for GPIOA
  RCC->APBENR2 |= 1<<17;  // Enable clock for TIM16

  // Configure PA5 as an output for the LED
  GPIOA->MODER &= ~(0b11<<10);
  GPIOA->MODER |=  (0b01<<10);

  // Timer: update rate of 1 kHz
  TIM16->PSC = 47;
  TIM16->ARR = 999;
  TIM16->DIER |= 1<<0;
  NVIC_EnableIRQ(TIM16_IRQn);
  TIM16->CR1 |= 1<<0;
}
void TIM16_IRQHandler(void) {
  if (TIM16->SR & (1<<0)) {
    TIM16->SR &= ~(1<<0);   // Clear flag
    GPIOA->ODR ^= (1<<5);    // Toggle LED on PA5
  }
}
int main(void){
  RegisterInit();
  while(1){
    // Empty superloop — the interrupt does all the work.
    // We still need it, or the program would just end.
  }
}
Demo — trick question Flash the board with this code. Is the timer interrupt actually firing and toggling the LED? Yes — just not visibly to a human eye. Toggling a pin 1000 times a second means it switches state every 0.5 ms, which is far faster than your eye's flicker threshold (~60 Hz / ~16 ms). It just looks constantly, dimly lit.
03 · EXAMPLES

Making it visible: a software counter riding on top

We want a blink a human can actually see — say, once per second. But we also want the accuracy of a fast, precise 1 kHz hardware tick. Solution: keep the hardware timer at 1 kHz, and count interrupts in software inside the ISR, only acting every 1000 of them.

void TIM16_IRQHandler(void) {
  if (TIM16->SR & (1<<0)) {
    TIM16->SR &= ~(1<<0);
    static uint16_t led_timer = 0;
    led_timer++;
    // Toggle every 1000 interrupts = every 1000 ms = 1 s
    if(led_timer >= 1000){
      led_timer = 0;
      GPIO_OutputTogglePin(GPIOA,5); // on 1s, off 1s → period 2s
    }
  }
}
Why static? A normal local variable is wiped out and recreated every time the function runs. static makes led_timer keep its value between calls — exactly what we need, since it has to keep accumulating across thousands of separate interrupts.

This is effectively a second, software-side prescaler stacked on top of the hardware one — useful whenever the delay you want is longer than a single 16-bit ARR can conveniently reach, or you want several different timings driven from one physical timer.

Cleaner code: wrapper functions

Notice how similar the setup code looks every time: enable a clock, configure some bits, enable an interrupt. Peripherals of the same type share the same register layout — GPIOA and GPIOB are identical structs at different addresses, and so are TIM16 and TIM17. That repetition is exactly what functions are for.

We write a small custom driver: a header file (declares what exists — types, function names) and a source file (defines how each function actually works).

#ifndef MY_STM_HELPER_H
#define MY_STM_HELPER_H
#include "stm32c0xx.h"
#include <stdbool.h>

typedef enum { GPIOA_BUS, GPIOB_BUS, TIM16_BUS, TIM17_BUS } PeripheralBus_t;
typedef enum { INPUT=0b00, OUTPUT=0b01, ALT=0b10, ANALOG=0b11 } GPIOMode_t;
typedef enum { NONE=0b00, PULL_UP=0b01, PULL_DOWN=0b10 } GPIOPull_t;

void Clock_Enable(PeripheralBus_t peripheral);
void GPIO_InitPin(GPIO_TypeDef *port, uint8_t pin, GPIOMode_t mode, GPIOPull_t pull);
void Timer_Init(TIM_TypeDef *timer, IRQn_Type irq_type, uint16_t psc, uint16_t arr, bool enable_interrupt);
void GPIO_OutputTogglePin(GPIO_TypeDef *port, uint8_t pin);

#endif
#include "my_stm_helper.h"

void Clock_Enable(PeripheralBus_t peripheral) {
  switch (peripheral) {
    case GPIOA_BUS: RCC->IOPENR  |= 1<<0;  break;
    case GPIOB_BUS: RCC->IOPENR  |= 1<<1;  break;
    case TIM16_BUS: RCC->APBENR2|= 1<<17; break;
    case TIM17_BUS: RCC->APBENR2|= 1<<18; break;
  }
}

void GPIO_InitPin(GPIO_TypeDef *port, uint8_t pin, GPIOMode_t mode, GPIOPull_t pull) {
  port->MODER &= ~(0b11 << (pin*2));
  port->MODER |=  (mode << (pin*2));
  port->PUPDR &= ~(0b11 << (pin*2));
  port->PUPDR |=  (pull << (pin*2));
}

void Timer_Init(TIM_TypeDef *timer, IRQn_Type irq_type, uint16_t psc, uint16_t arr, bool enable_interrupt) {
  timer->PSC = psc;
  timer->ARR = arr;
  if (enable_interrupt) {
    timer->DIER |= 1<<0;
    NVIC_EnableIRQ(irq_type);
  }
  timer->CR1 |= 1<<0;
}

void GPIO_OutputTogglePin(GPIO_TypeDef *port, uint8_t pin) {
  port->ODR ^= (1 << pin);
}

With the driver written once, main() becomes almost self-explanatory:

int main(void){
  Clock_Enable(GPIOA_BUS);
  Clock_Enable(TIM16_BUS);
  GPIO_InitPin(GPIOA, 5, OUTPUT, NONE);
  Timer_Init(TIM16, TIM16_IRQn, 47, 999, 1);  // 1 kHz, interrupts on
  while(1){ }
}
What's an enum, again? An enum (enumeration) defines a small named set of integer options, so a function call like GPIO_InitPin(GPIOA, 5, OUTPUT, NONE) reads like English instead of a string of magic numbers such as 0b01. It costs nothing at runtime and makes code dramatically easier for a human to check.

Example 2 — a pushbutton toggles the blinking

Same 1 kHz-driven, once-a-second LED blink on PA5 — but now a pushbutton on PB11 turns the blinking on and off. The button returns HIGH when not pressed (pulled up), so we watch for a falling edge. This reuses the EXTI (external interrupt) setup from Lecture 3.

The trick: two separate interrupts — the button's EXTI interrupt and the timer's update interrupt — communicate through one shared flag, is_blinking. The button ISR only flips the flag; the timer ISR is the only place that actually touches the LED.

#include "my_stm_helper.h"
volatile uint8_t is_blinking = 1; // shared between two ISRs → must be volatile

int main(void){
  Clock_Enable(GPIOA_BUS);
  Clock_Enable(GPIOB_BUS);
  Clock_Enable(TIM16_BUS);
  GPIO_InitPin(GPIOA, 5,  OUTPUT, NONE);
  GPIO_InitPin(GPIOB, 11, INPUT,  PULL_UP);
  EXTI_InitPin(EXTI_GPIOB, 11, FALLING, EXTI4_15_IRQn);
  Timer_Init(TIM16, TIM16_IRQn, 47, 999, 1);

  NVIC_SetPriority(TIM16_IRQn, 1);
  NVIC_SetPriority(EXTI4_15_IRQn, 2);
  while(1){ }
}
void EXTI4_15_IRQHandler(void){
  if (EXTI->FPR1 & (1<<11)){
    is_blinking = !is_blinking;      // flip on/off
    EXTI->FPR1 |= (1<<11);   // write 1 to clear the pending flag
  }
}
void TIM16_IRQHandler(void) {
  if (TIM16->SR & (1<<0)) {
    TIM16->SR &= ~(1<<0);
    static uint16_t led_timer = 0;
    if(is_blinking){
      led_timer++;
      if(led_timer>=1000){ led_timer=0; GPIO_OutputTogglePin(GPIOA,5); }
    } else{
      led_timer = 0;
      GPIO_OutputClearPin(GPIOA,5); // switch LED off
    }
  }
}
Why set priorities? NVIC_SetPriority tells the NVIC which interrupt should win if two arrive at almost the same instant. Here the timer (priority 1) outranks the button (priority 2 — remember, lower number usually means higher priority on Cortex-M), keeping the blink timing rock solid even if the button is mashed.
Refresher: what does EXTI_InitPin() actually do?

This is the EXTI driver from Lecture 3, reused here unchanged — it maps a GPIO pin to an EXTI interrupt line, picks which edge(s) to trigger on, and switches the NVIC line on.

void EXTI_InitPin(EXTIPort_t port, uint8_t pin, EXTITrigger_t trigger, IRQn_Type irq_type) {
  uint8_t idx   = pin / 4;         // which EXTICR register (0–3)
  uint8_t shift = (pin % 4) * 8;  // which 8-bit field inside it

  EXTI->EXTICR[idx] &= ~(0xFF << shift);
  EXTI->EXTICR[idx] |=  (port << shift);      // route this pin's port to the EXTI line

  EXTI->FTSR1 &= ~(1 << pin);
  EXTI->RTSR1 &= ~(1 << pin);
  if (trigger==EXTI_TRIGGER_FALLING || trigger==EXTI_TRIGGER_BOTH) EXTI->FTSR1 |= (1 << pin);
  if (trigger==EXTI_TRIGGER_RISING  || trigger==EXTI_TRIGGER_BOTH) EXTI->RTSR1 |= (1 << pin);

  EXTI->IMR1 |= (1 << pin);   // unmask (enable) this line
  EXTI->FPR1 |= (1 << pin);   // clear any stale pending flags first
  EXTI->RPR1 |= (1 << pin);
  NVIC_EnableIRQ(irq_type);
}
03 · EXAMPLES

The bounce problem

Run the button example on real hardware for a while and something odd happens: sometimes one press seems to toggle the LED two or three times instead of once. Nothing is wrong with your code — it's the switch itself.

A mechanical pushbutton isn't a perfect, instant connection. When you press it, the metal contacts physically bounce against each other for a few milliseconds before settling — a real switch closing rapidly, chaotically, on and off, many times in a row, before finally staying closed. Your EXTI pin sees every single one of those bounces as a separate falling edge, so it fires the interrupt several times for what felt like a single press.

What the pin actually sees when you press a button

A clean digital sensor doesn't have this problem — EXTI interrupts are fine for those. It's specifically mechanical switches that bounce.

The fix Ignore the noisy EXTI edge entirely for this button. Instead, use the timer — which is already running — to sample the pin at a steady, controlled rate (say, every 10 ms) and only trust the reading once it's been stable for several samples in a row. This is called debouncing, and it's exactly what LO2 asks you to implement.
03 · EXAMPLES

Example 3 — debouncing with a timer only

Drop the EXTI interrupt entirely. TIM16 is already firing at 1 kHz (once every 1 ms); we just count 10 of those to get a steady 10 ms sampling rate, and keep a short rolling history of the pin's readings.

The shift-register trick

Keep one byte, button_history, starting at 0xFF (all 1s — "released"). Every 10 ms: shift it left by one bit (making room, discarding the oldest sample) and OR in the pin's current reading at bit 0.

// Shift history left; new sample goes into bit 0
button_history = button_history << 1;
pin_state = GPIO_InputReadPin(GPIOB, 11);
if (pin_state) { button_history |= (1<<0); }  // record a HIGH sample

// Pull-up resistor: pin=1 → not pressed, pin=0 → pressed
// 0x80 = 0b10000000 → the last 7 samples were all LOW → safely "pressed"
if (button_history == 0x80) {
  is_blinking = !is_blinking;
}

Why 0x80 specifically, and not 0x00? Because 0x80 (0b10000000) only ever appears for one instant: exactly when the seven most-recent samples are all LOW and the sample eight steps ago was still HIGH — in other words, the precise moment a clean, sustained press has just been confirmed. It fires once per press, not continuously while held down.

Putting the full ISR together — a hardware timer running two independent jobs at once (debounce sampling and LED blinking) from a single 1 kHz tick:

void TIM16_IRQHandler(void) {
  if (TIM16->SR & (1<<0)) {
    TIM16->SR &= ~(1<<0);
    static uint16_t led_timer = 0;
    static uint16_t debounce_timer = 0;
    static uint8_t  button_history = 0xFF;
    static bool     pin_state = 1;

    debounce_timer++;
    if (debounce_timer >= 10) {           // every 10 ms
      debounce_timer = 0;
      button_history = button_history << 1;
      pin_state = GPIO_InputReadPin(GPIOB, 11);
      if (pin_state) { button_history |= (1<<0); }
      if (button_history == 0x80) { is_blinking = !is_blinking; }
    }

    if(is_blinking){
      led_timer++;
      if (led_timer >= 1000) { led_timer=0; GPIO_OutputTogglePin(GPIOA,5); }
    } else{
      led_timer = 0;
      GPIO_OutputClearPin(GPIOA,5);
    }
  }
}
Why this matters (LO2) This is a fully non-blocking debounce: the CPU is never stuck waiting, there's no software delay loop, and one hardware timer handles two completely different timing jobs simultaneously just by counting interrupts differently in software. This pattern — one fast, reliable hardware tick, with software counters layered on top for each job you need — is the single most reusable idea in this whole chapter.

The four formulas

f_tim = f_clk / (PSC+1)
T_tick = (PSC+1) / f_clk
T_update = (PSC+1)(ARR+1) / f_clk
f_update = f_clk / ((PSC+1)(ARR+1))

The setup sequence, every single time

Enable clock (RCC) → set PSC & ARR → enable interrupt (DIER) → enable NVIC line → enable counter (CR1) → handle & clear flag (SR) in the ISR

Glossary

Peripheral
A hardware sub-system built into the chip (a timer, a GPIO port, a UART...) controlled through registers.
Register
A named, addressable slot of bits that configures or reports on a peripheral.
Prescaler (PSC)
Divides the fast system clock down to a slower, usable timer clock.
Auto-reload (ARR)
The value CNT counts up to before resetting and firing an update event.
Update event
The moment CNT reaches ARR and resets — can be configured to raise an interrupt.
ISR
Interrupt Service Routine — the function that runs automatically when a peripheral interrupts the CPU.
NVIC
Nested Vectored Interrupt Controller — routes interrupt signals from peripherals to the CPU core.
Polling
Repeatedly checking a condition in software instead of waiting for an interrupt — simple but wastes CPU time.
Debounce
Filtering out the rapid electrical noise a mechanical switch produces when its contacts physically settle.
volatile
A C keyword that stops the compiler from caching a variable that can change outside normal program flow.
