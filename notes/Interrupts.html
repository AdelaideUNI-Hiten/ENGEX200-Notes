01 What are interrupts?

The problem: why polling isn't enough

Picture a car's Engine Control Unit (ECU). It watches a toothed metal wheel spinning with the crankshaft, using a sensor that reads 0 or 1 as each tooth passes. From the timing between teeth, the ECU works out exactly how fast the engine is spinning — and that number drives everything from fuel injection to ignition timing.

Doing the maths

The lecture uses a concrete number: 6000 RPM, a wheel with 60 teeth. Let's work out how much time we actually get per tooth.

6000 RPM → 6000 ÷ 60 = 100 revolutions per second = 100 Hz
One full revolution: T = 1/f = 1/100 = 0.01 s = 10 ms
60 teeth per revolution → time per tooth = 10 ms ÷ 60 ≈ 166.7 µs

That's the entire budget. Every 166.7 microseconds — a sliver of time far too short to blink an eye — a new tooth edge arrives, and the code must not miss it. This is safety-critical: a missed edge means a wrong speed reading, which can throw off fuel and ignition timing.

Option A: polling

Polling means: in your main loop, over and over, you check ("poll") the pin's register to see if it has changed. It's the most natural first idea — like refreshing a webpage every second to see if anything new happened, instead of waiting for a notification.

Skeleton polling code (crank-sensor example)
int main(void) {
    setup_registers();
    uint8_t  last_pin_state = 1;
    uint32_t cur_time = 0, prev_time = 0, delta_t = 0;

    while(1) {
        uint8_t cur_pin_state = read_crank_sensor();

        // Check for a falling edge
        if (last_pin_state == 1 && cur_pin_state == 0) {
            cur_time  = get_timer();
            delta_t   = cur_time - prev_time;
            prev_time = cur_time;

            fuel_injector_ops();   // ~30 µs
            update_dashboard();    // ~200 µs
        }
        last_pin_state = cur_pin_state;
    }
}
Why this fails: one pass through this loop, when the tooth-edge branch fires, costs roughly 30 µs + 200 µs ≈ 230 µs. But a new tooth arrives every 166.7 µs. The loop simply cannot get back around to check the pin fast enough — by the time it's free to look again, an edge (or more) may have already slipped past unseen. Result: an inaccurate, systematically slower-looking speed reading, at the exact moment accuracy matters most.
THINK OF IT LIKE THIS

Polling is like repeatedly picking up your phone every few seconds to see if a text arrived, instead of just letting it buzz. If something more important grabs your attention for a minute — you might completely miss that the text ever came in.

01 What are interrupts?

The fix: let the hardware tap you on the shoulder

An interrupt is a hardware-driven signal that forces the CPU to immediately drop whatever it's doing, run a small piece of code to handle the urgent event, and then return to exactly where it left off — as if nothing happened.

THINK OF IT LIKE THIS

You're doing homework (the main loop) when your phone rings (the interrupt). You don't need to keep glancing at it — the ring itself grabs your attention. You put your pen down, answer briefly ("yes, on my way" — the ISR), hang up, and pick your pen back up exactly where you stopped. You never had to waste time checking the phone every few seconds "just in case."

The little subroutine that runs when the interrupt fires is called an Interrupt Service Routine (ISR). Two rules the lecture stresses about ISRs:

  • You must set up what triggers the interrupt during system initialisation (which pin, which edge) — the hardware needs to be told what to watch for.
  • Keep the ISR minimal. The classic pattern is: just set a flag. Let the main loop do the heavy lifting when it's convenient, not while the CPU is stuck mid-interrupt.
The same crank-sensor problem, solved with an interrupt
volatile uint32_t cur_time = 0, prev_time = 0, delta_t = 0;
volatile uint8_t  tooth_flag = 0;   // Signal flag for the ISR

int main(void) {
    setup_interrupts();    // Tell the MCU: watch for a falling edge

    while(1) {
        update_dashboard();       // ~200 µs — runs continuously

        if (tooth_flag == 1) {
            tooth_flag = 0;       // Clear the flag
            fuel_injector_ops();  // ~30 µs
        }
    }
}

// Interrupt Service Routine — fires the instant a tooth edge is detected
void sensor_interrupt(void) {
    cur_time  = get_timer();
    delta_t   = cur_time - prev_time;
    prev_time = cur_time;

    tooth_flag = 1;   // Just raise the flag — that's it
}
Why this works: the hardware itself watches the pin, continuously, in parallel with whatever the CPU is doing. The instant a falling edge appears — even if the CPU is halfway through update_dashboard() — it pauses that function, jumps to the ISR, records the precise time, sets a flag, and resumes update_dashboard() exactly where it paused. No edge is ever missed, because nothing had to "get back around to checking."
Why volatile? Every shared variable above is declared volatile. Normally, a compiler is free to assume a variable doesn't change unless your visible code changes it, and may cache its value in a register instead of re-reading memory. But tooth_flag can change from inside the ISR at any moment — completely invisibly to the main loop's normal flow. volatile tells the compiler "don't assume — always read this fresh from memory," so the main loop actually notices when the ISR updates it.
One naming trap: a function named sensor_interrupt() looks fine to a human, but the microcontroller has no idea it's supposed to be an ISR — it's just a normal subroutine that nothing ever calls. The next section explains exactly what name it needs instead, and why.
01 What are interrupts?

NVIC — the interrupt traffic controller

So how does the CPU actually know an interrupt has occurred, and which code to run? That's the job of the Nested Vector Interrupt Controller (NVIC) — a piece of hardware built into every ARM Cortex-M chip.

The NVIC watches every peripheral that can raise an interrupt (timers, USB, ADC, external pins...) and, when one fires, looks up which piece of code should run and at what priority — because more than one interrupt can be waiting at once.

The vector table

Every possible interrupt source is pre-allocated a fixed address in memory, listed in a vector table in the chip's reference manual. Here's a real excerpt for the STM32C0 (RM0490, Table 56):

This is the row we'll use throughout this chapter: EXTI4_15 — the shared line for pin numbers 4 through 15. Full table: Chapter 13 of RM0490, Table 56, page 260.

The naming convention

ISR names aren't a style choice — they're a contract. The startup file (startup.s) already reserves an address in the vector table for each peripheral, tied to one exact function name. When you write a function with that exact name, the compiler slots your code into that pre-allocated address automatically. Get the name wrong, and your "ISR" is just dead code that never runs — silently.

Naming convention
Acronym_IRQHandler 
void EXTI4_15_IRQHandler(void){
    // This is the real, correctly-named ISR
}

This is exactly the fix for the naming trap from the previous section — sensor_interrupt() should have been named EXTI4_15_IRQHandler() (or whichever line the sensor pin actually falls on) to ever be invoked by the hardware.

01 What are interrupts?

EXTI — bridging GPIO to the CPU

The NVIC handles interrupts in general, but something has to actually watch the voltage on a GPIO pin and detect a rising or falling edge in the first place. That's the External Interrupt/Event Controller (EXTI) — it sits between the GPIO pins and the NVIC, acting purely as an edge detector for the physical world: button presses, encoder ticks, sensor pulses.

Pins are multiplexed by number, not by port

Here's the detail that catches people out: on the STM32C0, the EXTI lines are shared by pin number across every port. Pin 4 on Port A, Port B, Port C, Port D and Port F all feed into the very same line, EXTI4. Only one of them can be the source of a given interrupt at any moment.

Can't do: enable interrupts on PA4 and PB4 at the same time — same pin number, same EXTI line, direct conflict.
Totally fine: enable interrupts on PA4 and PB12 at the same time — different pin numbers, different EXTI lines. This is exactly the pairing used in the worked example later in this chapter.

When two ports share a line (e.g. EXTI4_15 covers pin numbers 4 through 15 on every port), they also share one ISR. Inside that ISR, your code checks a per-pin pending-flag bit to work out which physical pin actually triggered it.

02 GPIO interrupt registers

Meet the registers

Everything above was concept. Now let's get concrete: which actual memory addresses do you write to, to make an interrupt real? On the STM32C0, EXTI lives on the AHB bus at 0x4002 1800 – 0x4002 1BFF, and Chapter 14 of RM0490 documents six register groups you'll use:

RegisterJob
EXTI_EXTICRxChooses which port (A, B, ...) owns a given pin number's interrupt line.
EXTI_IMRxThe mask — unless a pin's bit is set here, its signal is blocked and never reaches the NVIC at all.
EXTI_RTSRx / EXTI_FTSRxChooses whether to watch for a rising or falling edge on that pin.
EXTI_RPRx / EXTI_FPRxThe pending flag — goes high the instant the edge you asked for actually happens. This is what your ISR checks.

Rising vs falling, and why it depends on your resistor

Pull-up resistorPin idles HIGH. A button press pulls it to ground → the pin goes high→low → that's a falling edge.
Pull-down resistorPin idles LOW. A button press pulls it to the supply voltage → the pin goes low→high → that's a rising edge.

Sensors like rotary encoders produce both edges on every tick, so it's common to arm both RTSR and FTSR on the same pin for extra precision.

External Interrupt Selection Register — EXTI_EXTICRx

There are four of these (EXTICR1–4), each 32 bits wide and split into four 8-bit lanes — one lane per pin number, holding a port code (0x00 = Port A, 0x01 = Port B, and so on).

EXTI_EXTICR3 (offset 0x068) — bits [23:16] hold EXTI10[7:0], the port code for pin 10

In code, EXTICR is defined as an array of 4 inside the EXTI struct, so EXTI_EXTICR3 is simply EXTI->EXTICR[2] (zero-indexed). Worked example — routing pin 10 to Port B:

EXTI->EXTICR[2] &= ~(0xFF<<16);  // clear the lane for pin 10
EXTI->EXTICR[2] |=  (0x01<<16);  // 0x01 = Port B

External Interrupt Mask Register — EXTI_IMRx

Configuring a pin's port doesn't switch it on by itself — by default every line is masked (blocked). One bit per pin number unmasks it:

EXTI->IMR1 |= (1<<10);  // Unmask pin 10 -> allowed to reach the NVIC

Trigger Selection — EXTI_RTSRx / EXTI_FTSRx

// Rising edge
EXTI->RTSR1 |= (1<<10);
// Falling edge
EXTI->FTSR1 |= (1<<10);

Pending Register — EXTI_RPRx / EXTI_FPRx

This is the flag that actually flips high the moment your chosen edge occurs — and the one your ISR inspects to know it has work to do. Reading and manually clearing it (by writing a 1 back) before you even arm the interrupt wipes out any stale bit left over from before setup.

EXTI->RPR1 |= (1<<10);  // rising-edge pending flag, pin 10
EXTI->FPR1 |= (1<<10);  // falling-edge pending flag, pin 10

03 Writing an interrupt service routine

The scenario

Time to put it all together with the lecture's running example: two independent pushbuttons, each toggling its own LED, both handled through interrupts.

Button 1 — PA4Wired with a pull-up (idle HIGH). Pressing it pulls the pin LOW → watch the falling edge. Controls LED1 on PA5.
Button 2 — PB11Wired with a pull-down (idle LOW). Pressing it pulls the pin HIGH → watch the rising edge. Controls LED2 on PB13.

Notice pin numbers 4 and 11 are different, so — per the EXTI muxing rule from Part 01 — both can safely share the single EXTI4_15_IRQHandler.

Code structure

Every STM32 interrupt-driven program follows the same skeleton. Get comfortable with this shape — you'll reuse it constantly:

#include "stm32c0xx.h"

volatile uint8_t PA4_button  = 0;  // software flag for Button 1
volatile uint8_t PB11_button = 0;  // software flag for Button 2

void SystemInit(void){
    // STM32 startup subroutine — leave empty.
    // startup.s already has a dedicated address for this.
}

void RegisterInit(void){
    // All register/interrupt configuration goes here
}

void EXTI4_15_IRQHandler(void){
    // The ISR — invoked automatically when an interrupt is detected
}

int main(void){
    RegisterInit();
    while(1){ /* do something */ }
}
Four moving parts, one job each: SystemInit stays empty (it's a startup hook, not yours to use), RegisterInit configures hardware once, the _IRQHandler reacts to events, and main's infinite loop does the ongoing work.
03 Writing an interrupt service routine

Register initialisation, line by line

This is the real RegisterInit() from the lecture. Every line does exactly one small thing — read it as a checklist, not a wall of code.

Step 1 — GPIO clocks, pin directions, pull resistors

RCC->IOPENR |= (1<<0 | 1<<1);
Peripherals are asleep (clock-gated) until you switch their clock on. This enables the clock for both GPIOA and GPIOB in one line — nothing on a port works until its clock is running.
GPIOA->MODER &= ~(0b11<<10);
GPIOA->MODER |= 0b01<<10;
Clear then set the 2-bit mode field for PA5 (LED1) to 01 = general-purpose output.
GPIOA->MODER &= ~(0b11<<8);
GPIOA->PUPDR &= ~(0b11<<8);
GPIOA->PUPDR |= 0b01<<8;
Leave PA4 (Button 1) as 00 = input (clearing MODER is enough), then set its pull register to 01 = internal pull-up — matching the "idle HIGH, watch falling" plan.
GPIOB->MODER &= ~(0b11<<26);
GPIOB->MODER |= 0b01<<26;
Same idea for PB13 (LED2): set to output mode.
GPIOB->MODER &= ~(0b11<<22);
GPIOB->PUPDR &= ~(0b11<<22);
GPIOB->PUPDR |= 0b10<<22;
PB11 (Button 2) stays an input, pull register set to 10 = internal pull-down — "idle LOW, watch rising."

Step 2 — arm the EXTI lines for both buttons

EXTI->EXTICR[1] &= ~(0xFF<<0);
EXTI->EXTICR[1] |= 0x00<<0;
Pin 4 → EXTICR[1] (⌊4/4⌋), byte 0. Route it to Port A (0x00). This line is technically redundant since the register resets to all-zero — but it documents intent.
EXTI->IMR1 |= (1<<4);
Unmask pin 4.
EXTI->FTSR1 |= (1<<4);
Watch the falling edge — PA4 is pulled up, so a press pulls it low.
EXTI->FPR1 |= (1<<4);
Defensively clear any stale falling-edge pending bit for pin 4 before we arm things.
EXTI->EXTICR[2] &= ~(0xFF<<24);
EXTI->EXTICR[2] |= 0x01<<24;
Pin 11 → EXTICR[2] (⌊11/4⌋), byte 3 (shift 24). Route it to Port B (0x01).
EXTI->IMR1 |= (1<<11);
Unmask pin 11.
EXTI->RTSR1 |= (1<<11);
Watch the rising edge — PB11 is pulled down, so a press pulls it high.
EXTI->RPR1 |= (1<<11);
Defensively clear any stale rising-edge pending bit for pin 11.
NVIC_SetPriority(EXTI4_15_IRQn, 1);
NVIC_EnableIRQ(EXTI4_15_IRQn);
These are ARM Cortex-M0+ core functions (from the CMSIS programming manual, not RM0490). Both pins land on the EXTI4_15 line, so this one pair of calls arms the shared line for both buttons at once.

Naming convention to remember: NVIC_SetPriority / NVIC_EnableIRQ both take a PeripheralAcronym_IRQn value — the "n" for "number," as opposed to the _IRQHandler function itself.

03 Writing an interrupt service routine

The ISR

Both buttons trigger the exact same handler function, so the code inside must check which pin actually caused it — using each pin's own pending-flag bit:

void EXTI4_15_IRQHandler(void){
    // Did PA4 (Button 1) fall?
    if (EXTI->FPR1 & (1<<4)){
        PA4_button = 1;             // raise the software flag
        EXTI->FPR1 |= (1<<4);      // write 1 to CLEAR bit 4 (it's rc_w1)
    }
    // Did PB11 (Button 2) rise?
    if (EXTI->RPR1 & (1<<11)){
        PB11_button = 1;
        EXTI->RPR1 |= (1<<11);     // write 1 to CLEAR bit 11
    }
}
The single most common bug here: the pending register is rc_w1 — "read/clear, write 1." Writing a 1 clears the bit; writing 0 does nothing. Forget to clear it, and the instant the ISR returns, the NVIC sees the flag is still set and immediately re-enters the same ISR — forever. This looks like a total system freeze.

Notice how little happens in here: check a bit, set a flag, clear a bit. All the actual "do something" work (toggling an LED) is deliberately left for main() — exactly the minimal-ISR principle from Part 01.

03 Writing an interrupt service routine

The main loop

int main(void){
    RegisterInit();
    while(1){
        if(PA4_button){
            GPIOA->ODR ^= (1<<5);   // toggle LED1 (XOR flips just this bit)
            PA4_button = 0;          // clear the flag, or this retriggers forever
        }
        if(PB11_button){
            GPIOB->ODR ^= (1<<13);  // toggle LED2
            PB11_button = 0;
        }
    }
    return 0;
}
Why XOR (^=)? XOR-ing a bit with 1 flips it: 0→1 and 1→0. That's exactly "toggle" — one press turns the LED on, the next press turns it off — without needing to know the LED's current state.
Why clear the software flag too? The hardware pending bit was already cleared inside the ISR. This second flag is pure software — if you don't reset it to 0, the very next loop iteration would think the button was pressed again and toggle the LED a second time on its own.
§ Review

Key terms

Interrupt
A hardware signal that pauses normal execution to run urgent code, then resumes exactly where it left off.
Polling
Repeatedly checking a pin's state in a software loop — simple, but can miss fast or unpredictable events.
ISR
Interrupt Service Routine — the function that runs when an interrupt fires. Keep it short.
NVIC
Nested Vector Interrupt Controller — the ARM Cortex-M hardware that manages every interrupt source and its priority.
Vector table
The fixed list mapping every interrupt source to a memory address and a required handler function name.
EXTI
External Interrupt/Event Controller — detects rising/falling edges on GPIO pins and reports them toward the NVIC.
Mask (IMR)
A register that must be explicitly set to "unmask" a pin before its interrupt is allowed through at all.
Pending flag
Goes high the instant the chosen edge occurs; the ISR reads it to know who fired, then must clear it (write 1).
Rising / falling edge
A pin transitioning low→high (rising) or high→low (falling).
Pull-up / pull-down
An internal resistor that holds a floating pin at a known idle level (HIGH or LOW) until something actively pulls it the other way.
volatile
A C keyword telling the compiler a variable can change unexpectedly (e.g. inside an ISR), so it must always be re-read from memory.
Priority
When multiple interrupts are pending, the NVIC uses priority levels to decide which runs first.

§ Review

Summary

LO1 — what an interrupt is

Polling wastes CPU time and can miss fast events because the loop can't check fast enough. An interrupt lets hardware watch a pin in parallel and tap the CPU on the shoulder only when something actually happens. The NVIC routes every interrupt source to a fixed vector-table address and a strictly-named handler; the EXTI controller is the piece that specifically watches GPIO pins for rising/falling edges, with pins multiplexed by number across ports.

LO2 — how to write one on the STM32

Configure four register groups per pin — EXTICR (port), IMR (mask/enable), RTSR/FTSR (edge direction), RPR/FPR (pending flag) — then arm the shared line with NVIC_SetPriority and NVIC_EnableIRQ. Inside the _IRQHandler, check each pin's pending bit, set a software flag, and clear the pending bit (it's write-1-to-clear). Do the real work — toggling an LED, updating state — back in main(), and always mark shared variables volatile.
