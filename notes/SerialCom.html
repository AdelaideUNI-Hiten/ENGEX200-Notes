Serial Communication
with UART

Two chips, no shared clock, no idea what the other one is currently doing — and yet they manage to hold a reliable conversation down a single wire, one bit at a time. This is how, and why every register bit exists for a reason.

Part 01 · What is USART?

Why we even need this

So far in this course, you've mostly been flipping one pin at a time — turning an LED on, generating one PWM signal for one servo. That doesn't scale.

Imagine you wire up an external device to your microcontroller, and that device needs to receive the byte 0x0A (binary 0000 1010) to change state. If you send all 8 bits at once, in parallel, you need 8 separate output pins just for that one device — one wire per bit, all changing simultaneously.

The problem Now imagine n devices like this. You very quickly run out of physical pins on the chip. A microcontroller might have 20–50 GPIO pins; a handful of parallel devices can eat all of them just for data lines, before you've even wired up the rest of your project.

The fix is to stop sending bits in parallel and send them one after another, down a single wire — i.e. turn parallel data into a serial stream. That's literally what the hardware peripheral we're studying does:

USART = Universal Synchronous/Asynchronous Receiver–Transmitter

A hardware block built into the MCU that converts parallel data (many bits at once, inside the chip) into a serial stream (one bit at a time, on a wire) — and does the reverse for incoming data.

With this peripheral, you need just two wires, regardless of how many bits per message you're sending:

  • Tx (Transmit) — the line this device uses to send data
  • Rx (Receive) — the line this device uses to receive data
Asynchronous vs. Synchronous This lecture covers asynchronous serial communication (UART) — no shared clock wire at all, just Tx and Rx. Synchronous communication (like SPI, which adds a shared clock line) is covered in a later lecture series.

Meet UART / USART

Quick terminology check, because both names get used interchangeably.

TermMeaning
USARTThe full peripheral name — capable of both synchronous and asynchronous operation.
UARTThe same peripheral, but specifically being used in its asynchronous mode (no clock line). This is what this whole lecture is about.

The Nucleo C031C6 has two USART peripherals on board — USART1 and USART2. They live on the same internal bus (the APB bus) and share an identical register map, so everything you learn about configuring one applies directly to the other.

Baud rate — agreeing on a tempo

Here's the core problem with asynchronous communication: the transmitter and receiver do not share a clock signal. So how does the receiver know exactly when to "look" at the wire to read each bit?

The answer: both sides agree, in advance, on exactly how fast bits will be sent. This speed is called the baud rate, measured in bits per second (bps). Common values are 9600 and 115200 bps.

Think of it like this It's like two people agreeing beforehand to speak in exact, metronome-timed syllables — say, one syllable every 100 ms — without an actual metronome ticking between them. As long as both sides start counting at the same moment and use the same tempo, the listener can figure out where each syllable begins and ends, purely from time.

Once you know the baud rate, you know exactly how long one bit takes to transmit:

bit time = 1 / baud rate

At 115 200 bps: 1 / 115200 = 8.68 µs per bit — both transmitter and receiver must be configured to the same baud rate, or the bits will be sampled at the wrong moments and the data will come out as garbage.

Turning "baud rate" into a register value: BRR

The USART peripheral doesn't take "115200" as an input directly. Instead, you configure a divider in the Baud Rate Register (BRR), which divides down the peripheral's input clock (fclk) to produce your target baud rate:

Desired Baud Rate = fclk / BRR

Rearranged to solve for the register value you actually need to write: BRR = fclk / baud — rounded to the nearest whole number, since a register can't hold a fraction.

Framing a byte: start & stop bits

Knowing the tempo (baud rate) isn't quite enough. The receiver also needs to know when a byte begins, since there's no separate "here comes data" wire either.

UART solves this with a clever trick using the line's idle state:

  • When nothing is being sent, the wire is held HIGH — this is called idle.
  • To announce "a byte is coming", the transmitter pulls the line LOW for exactly one bit-time. This is the start bit.
  • The 8 data bits follow immediately, each held for one bit-time, at whatever level (high/low) represents that bit.
  • After the 8th bit, the line is pulled back HIGH for one bit-time — the stop bit — then returns to idle (also high).
Easy to miss on the slide The 8 data bits are sent least-significant bit (LSB) first, not the order you'd normally read a binary number. 0x0A is 0000 1010 written the normal way (MSB first), but on the wire it goes out as bit0, bit1 … bit7 → 0,1,0,1,0,0,0,0.

This whole scheme — 8 data bits, no parity bit, 1 stop bit — is nicknamed 8N1, and it's the default and most common UART configuration. (Variants with 7 or 9 data bits, or an added parity bit, exist but aren't covered in this course.)

Notice the timing: 1 / baud rate is the width of every single segment above — start bit, each data bit, and the stop bit all take exactly one bit-time. The receiver just needs to sample the line at that same interval, starting from the moment it detects the falling edge of the start bit.

The bottleneck problem

Fine — we can send a byte. But what happens when data keeps arriving, byte after byte, while your CPU has other jobs to do?

At 115 200 bps, one full 8N1 frame is 10 bits (1 start + 8 data + 1 stop), which takes 86.8 µs to transmit. If your code naively fires an interrupt service routine (ISR) to read every single incoming byte, that ISR gets invoked roughly every 86.8 µs.

Why this matters If your program is also running something else time-sensitive — a PWM control loop for a servo, for example — constantly interrupting it every 86.8 µs to service one UART byte can starve that other task of CPU time, causing it to misbehave or "crash".

Two complementary fixes exist for this: a small buffer built into the hardware, and a bigger one you manage yourself in software.

Hardware buffer (FIFO)

The STM32 USART peripheral includes a small hardware queue — typically 8 bytes — that sits between the wire and the CPU. Incoming bytes pile up here First In, First Out (FIFO), and the CPU is only interrupted once a configurable amount has accumulated, called the threshold:

Threshold settingBytes (of 8)
25%2 bytes
50%4 bytes
75%6 bytes
100%8 bytes (full)

Once the buffer holds that many bytes, an interrupt fires and hands the whole batch to the CPU at once — dramatically cutting down how often the CPU gets interrupted, at the cost of a little extra latency.

Software ring buffer

Is 8 bytes always enough? Definitely not — think about a GPS module on a drone streaming continuous location sentences, or a user typing a long command. If the CPU is busy elsewhere and the hardware FIFO fills up completely, new incoming data gets silently lost (an "overrun").

The standard fix: as soon as the hardware FIFO has data, a hardware interrupt drains it into a much bigger buffer sitting in ordinary RAM — a software ring buffer. This is just a fixed-size array with two independent index pointers:

  • head (write index) — where the next incoming byte from the ISR will be written
  • tail (read index) — where your main program will read the next byte from

When either pointer reaches the last slot, it wraps back around to index 0 — hence "ring". You do this with modulo arithmetic:

idx = (idx + 1) % N;              // works for any buffer size N
idx = (idx + 1) & (N - 1);        // faster: only valid if N is a power of 2
Full vs. empty — a subtle gotcha head == tail means the buffer is empty — everything written has been read. But if you let a write make head catch back up to tail, a completely full buffer would look identical (also head == tail)! The standard trick: stop writing once there is exactly one empty slot left, i.e. treat (head + 1) % N == tail as "full". You sacrifice one slot of capacity to keep full and empty distinguishable.

Part 02 · UART Registers

Wiring the pins: Alternate Function mode

The Tx/Rx signals don't come out of just any pin. Before UART can use a physical GPIO pin, that pin has to be told "you are not a plain digital I/O right now — you belong to a peripheral".

This is done through two GPIO registers:

GPIOx_MODER — 2 bits per pin
ValueMode
00Input
01General purpose output
10Alternate function — hands the pin over to a peripheral (timer, SPI, UART, etc.)
11Analog

Once a pin is in Alternate Function mode, you still need to say which peripheral function it should carry — a single pin can usually be routed to several different peripherals. That's what the Alternate Function register is for:

  • GPIOx→AFR[0] — configures pins Px0–Px7
  • GPIOx→AFR[1] — configures pins Px8–Px15
On the Nucleo C031C6 The demo project in this lecture wires PA2 → USART2 Tx and PA3 → USART2 Rx (see the User Manual um2593, Table 12, for the full pin map). In code: 
GPIO_InitPin(GPIOA, 2, ALT, NONE);   // PA2 set to Tx
GPIO_SetAltFcn(GPIOA, 2, 1);      // select the correct AF (alternate function) number
GPIO_InitPin(GPIOA, 3, ALT, NONE);   // PA3 set to Rx
GPIO_SetAltFcn(GPIOA, 3, 1);      // select the correct AF number

The Control Register — USART_CR1

This is the main on/off switch panel for the whole peripheral. Two USARTs on this chip (USART1, USART2) — same register layout for both, sitting on the APB bus (see Chapter 26 of the STM32C0 reference manual, RM0490).

Key bits you'll actually touch in this course (highlighted below, out of the full 32-bit register):

BitNameMeaning
0UEUSART Enable — the master on/off switch. Keep this off while you configure everything else.
2REReceiver Enable — turns the Rx line on.
3TETransmitter Enable — turns the Tx line on.
5RXNEIEEnables an interrupt whenever a new byte has fully arrived (FIFO mode off).
7TXEIEEnables an interrupt whenever the transmit register is empty and ready for more data (FIFO mode off).
12M0Word-length bit (paired with M1 below).
28M1Word-length bit — M1:M0 = 00 → 8 bits (default) · 01 → 9 bits · 10 → 7 bits.
29FIFOENTurns on the hardware FIFO queue (see the FIFO section below).

Moving the actual bytes: BRR, RDR, TDR

Three more registers, and they're much simpler than CR1.

RegisterFull nameWhat it does
BRRBaud Rate RegisterSets the baud rate relative to the peripheral clock — see the calculator above: BRR = fclk / baud.
RDRReceive Data Register (9-bit)Holds the most recently received byte. Just read this register to get the incoming data.
TDRTransmit Data Register (9-bit)Write the byte you want to send here — the hardware shifts it out over Tx automatically.

Both data registers are 9 bits wide (not 8) so they can also carry the optional 9-bit word length mode mentioned above.

Interrupt-driven Rx and Tx (FIFO disabled)

Rather than constantly polling "has a byte arrived yet?" in a loop, you can let the hardware tell you the instant something needs attention.

Receiving

Enable RXNEIE in CR1

Alongside RE and UE. This is the "tell me when a byte lands" switch.

A byte arrives

The hardware automatically sets the RXNE (Read Data Register Not Empty) flag in the Interrupt Status Register (ISR), which triggers your ISR.

Read USART→RDR

Reading the register gets you the byte — and automatically clears RXNE for you. You never need to clear it manually in code; the hardware detects the read.

Transmitting

Enable TXEIE in CR1

Alongside TE and UE. This is the "tell me when I can send the next byte" switch.

TDR becomes empty

The hardware sets the TXE (Transmit Empty) flag in ISR, triggering your ISR to supply the next byte.

Write to USART→TDR

This clears TXE automatically; it gets set again once that byte has finished shifting out.

Turn TXEIE back off when done

Once your whole message has been transmitted, disable TXEIE — otherwise the ISR keeps firing forever with nothing left to send.

Overrun errors If a new byte finishes arriving before the previous one has been read out of RDR, the old byte is lost and the ORE (Overrun Error) flag is set in ISR. You clear it by writing to the ORECF bit in the Interrupt Clear Register (USART→ICR) — most STM32 status flags that need manual clearing follow this same "write to the matching bit in ICR" pattern.

Turning on FIFO mode & setting thresholds

Setting FIFOEN = 1 in CR1 activates the 8-byte hardware queue discussed earlier. You still read from RDR and write to TDR exactly as before — the hardware silently manages the queue behind those same two registers.

With FIFO mode on, by default the interrupt would still fire on every single byte (via RXFNEIE/TXFNEIE — the FIFO-mode equivalents of RXNEIE/TXEIE). To actually get the CPU-saving benefit, you configure a threshold in USART_CR3 instead:

Bit(s)NameMeaning
23TXFTIEEnable an interrupt when the Tx FIFO reaches its configured threshold.
25–27RXFTCFG3-bit Rx threshold level (table below).
28RXFTIEEnable an interrupt when the Rx FIFO reaches its configured threshold.
29–31TXFTCFG3-bit Tx threshold level (table below).

RXFTCFG (Rx: fires once this full)

0001/8 full (1 byte)
0011/4 full (2 bytes)
0101/2 full (4 bytes)
0113/4 full (6 bytes)
100Full (8 bytes)

TXFTCFG (Tx: fires once this empty)

0001/8 full (1 byte)
0011/4 full (2 bytes)
0101/2 full (4 bytes)
0113/4 full (6 bytes)
100Empty (0 bytes)

In the status register ISR, the flags to watch become RXFNE/RXFT (receive side) and TXFNF/TXFT (transmit side) — the hardware clears RXFNE automatically once the FIFO queue empties out.

Part 03 · UART Examples

Worked example: servo control over UART

Everything above, put together into one real project from the lecture: a three-servo rig, controlled by typing commands into a serial terminal.

You open a serial monitor on your computer, connected to the Nucleo board, and type something like S0:90 and hit Enter.

  • That text is RECEIVED (Rx) on the Nucleo, byte by byte
  • The MCU parses it, moves servo 0 to 90°
  • The MCU TRANSMITS (Tx) an acknowledgment message back to the serial monitor, e.g. [ACK] Servo updated

The basic flow

main()Initialisation, then loops calling USART_ProcessRxBuffer()
├──▶
Servo_SetAngle()Generates the PWM signal that physically moves the motor
└──▶
USART_SendString()Writes the acknowledgment characters into TDR
⋮ (interrupt, any time)
USART2_IRQHandler()Reads new bytes from RDR into the ring buffer · writes queued acknowledgment bytes into TDR

Code walkthrough

The complete implementation, broken into the pieces you'd actually write, in the order they run.

void USART_Init(USART_TypeDef *usart, uint32_t sys_clk, uint32_t baud,
                USART_Thresh_t fifo_threshold_rx, USART_Thresh_t fifo_threshold_tx,
                bool enable_rx_irq, bool enable_tx_irq) {

    usart->CR1 &= ~(1 << 0);              // Disable USART before configuring it (UE = 0)
    usart->BRR  = (sys_clk / baud);       // Set the Baud Rate Register

    // Clear RE(2), TE(3), RXNEIE(5), TXEIE(7), FIFOEN(29) first
    usart->CR1 &= ~((1 << 2) | (1 << 3) | (1 << 5) | (1 << 7) | (1 << 29));
    usart->CR1 |=  (1 << 2) | (1 << 3);   // Enable Rx and Tx

    // Clear FIFO threshold config + interrupt-enable bits in CR3
    usart->CR3 &= ~((0b111 << 29) | (1 << 28) | (0b111 << 25) | (1 << 23));

    if (fifo_threshold_rx != FIFO_NONE || fifo_threshold_tx != FIFO_NONE) {
        usart->CR1 |= (1 << 29);          // Enable Hardware FIFO

        if (fifo_threshold_rx != FIFO_NONE) usart->CR3 |= (fifo_threshold_rx << 25);
        if (fifo_threshold_tx != FIFO_NONE) usart->CR3 |= (fifo_threshold_tx << 29);
        if (enable_rx_irq) usart->CR3 |= (1 << 28);   // RXFTIE
        if (enable_tx_irq) usart->CR3 |= (1 << 23);   // TXFTIE

    } else {
        usart->CR1 &= ~(1 << 29);         // Disable Hardware FIFO
        if (enable_rx_irq) usart->CR1 |= (1 << 5);   // RXNEIE
        if (enable_tx_irq) usart->CR1 |= (1 << 7);   // TXEIE
    }

    // Enable the matching NVIC interrupt line if any Rx/Tx interrupt requested
    if (enable_rx_irq || enable_tx_irq) {
        if      (usart == USART1) NVIC_EnableIRQ(USART1_IRQn);
        else if (usart == USART2) NVIC_EnableIRQ(USART2_IRQn);
    }

    usart->CR1 |= (1 << 0);   // Configuration complete — enable USART (UE = 1)
}

Notice the pattern: disable (UE = 0) → configure every register → re-enable (UE = 1) at the very end. Configuring a live, running peripheral leads to undefined behaviour on most STM32 parts.

bool USART_SendChar(USART_TypeDef *usart, char c) {
    uint8_t next_head = (usart_tx_head + 1) % TX_BUF_SIZE;

    if (next_head == usart_tx_tail) {
        return false;               // ring buffer is full — refuse the write
    }

    usart_tx_buf[usart_tx_head] = c;    // store the character
    usart_tx_head = next_head;          // advance head, wrapping via %

    if (usart->CR1 & (1 << 29)) usart->CR3 |= (1 << 23);  // FIFO enabled: TXFTIE
    else                             usart->CR1 |= (1 << 7);   // FIFO disabled: TXEIE

    return true;
}

bool USART_SendString(USART_TypeDef *usart, const char *str) {
    // Walk the string, sending one character at a time
    while (*str) {
        if (!USART_SendChar(usart, *str++)) {
            return false;   // buffer overflowed mid-string
        }
    }
    return true;
}

This is exactly the ring-buffer write path from the widget above — USART_SendChar only ever enables the transmit interrupt; it never writes to TDR directly. The ISR (next tab) does that.

int main(void) {
    Clock_Enables...
    Servo_Timer_config...

    GPIO_InitPin(GPIOA, 2, ALT, NONE);   // PA2 set to Tx
    GPIO_SetAltFcn(GPIOA, 2, 1);
    GPIO_InitPin(GPIOA, 3, ALT, NONE);   // PA3 set to Rx
    GPIO_SetAltFcn(GPIOA, 3, 1);

    USART_Init(USART2, 48000000, 115200, FIFO_NONE, FIFO_NONE, true, true);

    USART_SendString(USART2, "Servo Command System Ready!\r\n");

    while (1) {
        USART_ProcessRxBuffer();
    }
}

The main loop does almost nothing itself — it just keeps calling USART_ProcessRxBuffer(). All the real-time work (catching bytes off the wire) happens in the interrupt handler, running independently of whatever main() is doing.

void USART2_IRQHandler(void) {

    // --- Rx: FIFO threshold (bit 28) OR plain RXNE (bit 5) ---
    if ((USART2->ISR & (1 << 28)) || (USART2->ISR & (1 << 5))) {
        char c = (char)USART2->RDR;         // reading RDR clears the flag automatically
        uint8_t next = (rx_head + 1) % RX_BUF_SIZE;
        if (next != rx_tail) {
            rx_ring_buf[rx_head] = c;
            rx_head = next;
        }  // else: buffer full, byte is dropped
    }

    // --- Tx: FIFO threshold (bit 23) OR plain TXE (bit 7) ---
    if ((USART2->ISR & (1 << 23)) || (USART2->ISR & (1 << 7))) {
        USART_TX_ISR_Handler(USART2);   // echoes / sends the next queued byte
    }
}

void USART_TX_ISR_Handler(USART_TypeDef *usart) {
    if (usart_tx_tail != usart_tx_head) {
        usart->TDR = usart_tx_buf[usart_tx_tail];      // send the next queued byte
        usart_tx_tail = (usart_tx_tail + 1) % TX_BUF_SIZE;
    } else {
        // nothing left to send — turn the interrupt back off
        if (usart->CR1 & (1 << 29)) usart->CR3 &= ~(1 << 23);  // clear TXFTIE
        else                             usart->CR1 &= ~(1 << 7);   // clear TXEIE
    }
}

This is the "turn TXEIE back off when done" step from earlier, shown in real code — otherwise this ISR would fire endlessly with an empty buffer.

void USART_ProcessRxBuffer(void) {
    static char line_buf[32];
    static uint8_t line_pos = 0;
    char echo_buf[2] = {0};

    while (rx_tail != rx_head) {
        char c = rx_ring_buf[rx_tail];
        rx_tail = (rx_tail + 1) % RX_BUF_SIZE;

        // Echo the keystroke straight back so the user sees what they typed
        if (c != '\r' && c != '\n') {
            echo_buf[0] = c;
            USART_SendString(USART2, echo_buf);
        }

        // Enter pressed → try to parse a full command line
        if (c == '\r' || c == '\n') {
            if (line_pos > 0) {
                line_buf[line_pos] = '\0';
                int id = 0, angle = 0;

                if (sscanf(line_buf, "S%d:%d", &id, &angle) == 2) {
                    Servo_SetAngle(id, angle);
                    USART_SendString(USART2, "[ACK] Servo updated\r\n");
                } else {
                    USART_SendString(USART2, "[ERR] Invalid Command\r\n");
                }
                line_pos = 0;
            }
        } else if (line_pos < sizeof(line_buf) - 1) {
            line_buf[line_pos++] = c;
        }
    }
}

This is where the ring buffer finally gets drained. It builds up a text line character by character until Enter (\r or \n) arrives, then uses sscanf to pull a servo ID and angle out of a command like S0:90.

Cheat sheet & recap

Learning outcomes — can you do this now?

  • Explain why parallel wiring doesn't scale, and how UART turns parallel data into a serial stream over just two wires (Tx/Rx).
  • Explain why an asynchronous link needs an agreed baud rate, and calculate BRR from a target baud rate and fclk.
  • Draw or read an 8N1 frame: idle high → start bit low → 8 data bits (LSB first) → stop bit high → idle.
  • Explain why interrupting on every byte doesn't scale, and how hardware FIFOs + thresholds reduce interrupt frequency.
  • Implement a software ring buffer with head/tail pointers, including the wraparound and full/empty conditions.
  • Identify the key USART registers (CR1, CR3, BRR, RDR, TDR, ISR, ICR) and the bits inside them used in this course.

Setup sequence, every single time

Enable peripheral clocks

For both the GPIO port and the USART peripheral.

Configure Tx/Rx pins

Alternate Function mode in MODER, correct function number in AFR.

Disable the USART

UE = 0 — never configure a live peripheral.

Set the baud rate

Write BRR = fclk / baud.

Enable Rx / Tx

RE and/or TE; enable FIFOEN + thresholds if you want FIFO mode.

Enable the interrupts you need

RXNEIE/TXEIE (no FIFO) or RXFTIE/TXFTIE (FIFO).

Enable the NVIC line

NVIC_EnableIRQ(USARTx_IRQn) — without this, the interrupt never reaches your handler.

Enable the USART

UE = 1 — configuration complete, peripheral goes live.

Handle it in the ISR

Check the relevant ISR flags, read RDR / write TDR, and shuffle bytes through your ring buffers.

Glossary

UART
Universal Asynchronous Receiver-Transmitter — a USART used without a shared clock line.
USART
Universal Synchronous/Asynchronous Receiver-Transmitter — the general hardware peripheral.
Baud rate
The agreed transmission speed, in bits per second.
BRR
Baud Rate Register — divides the peripheral clock down to the target baud rate.
Start / stop bit
Framing bits that mark the beginning and end of a byte on an otherwise idle-high line.
8N1
8 data bits, no parity bit, 1 stop bit — the standard UART frame format used in this course.
Tx / Rx
Transmit / Receive — the two data lines used in UART.
FIFO
First In, First Out — the small hardware queue that buffers bytes before they reach the CPU.
Threshold
The FIFO fill/drain level at which an interrupt is triggered, instead of on every byte.
Ring buffer
A fixed-size array in RAM with wrapping head/tail indices, used to buffer far more data than the hardware FIFO can hold.
Head / tail
The write index / read index of a ring buffer.
Overrun (ORE)
An error flag set when a new byte overwrites one that hasn't been read yet.
ISR
Interrupt Service Routine — the function that runs when a hardware interrupt fires. Also the name of USART's own status register — context tells them apart.
NVIC
Nested Vectored Interrupt Controller — the chip-wide controller that must be told to let a peripheral's interrupt through.
AFR / MODER
GPIO registers that select a pin's alternate function and overall mode (input/output/AF/analog).
