Part 1

The big picture

Before we touch a single register, it helps to know what a microcontroller physically is and how its pieces talk to each other.

1.1  What actually is a microcontroller?

Think of a laptop: a CPU, memory, and storage, but as three separate chips wired together on a big motherboard, plus a fan, a screen, a battery... A microcontroller squashes the essentials of that — a processor, some memory, and connections to the outside world — onto a single, tiny chip. No operating system, no screen, nothing decorative. Just enough to run one program and talk to real-world hardware: LEDs, motors, sensors, buttons.

This course uses two specific boards, both built around STMicroelectronics chips (the "STM32" family):

"Cortex-M0+" and "Cortex-M4" are Arm's processor designs — M0+ is the smallest and simplest, M4 is faster and can do more advanced maths (useful for signal processing). Everything you learn about addressing and registers here applies to both, and to essentially every Arm Cortex-M chip on the market.

1.2  System architecture: a highway with numbered exits

The Arm Cortex-M core is the brain of the chip — it's the only part that actually executes your code. But the brain is useless on its own; it needs to read your program out of memory, store variables somewhere, and flip pins on and off. All of that traffic — CPU to memory, CPU to GPIO pins, CPU to timers — travels along an internal bus matrix: essentially a highway system connecting the CPU to every other block on the chip.

Every block sitting on that highway is reached by driving to a specific address, the same way you'd drive to a specific street number. That's the entire idea behind a memory map, and it's why the next section matters so much.

Good to know

Most peripherals — timers, I2C, SPI, UART, the ADC — are switched off by default when the chip powers up, to save energy. Before you can use one, you need to enable its clock signal through a block called the RCC (Reset and Control Clock). More on that in Part 3.

The CPU

Executes your compiled code, instruction by instruction. It cannot "see" hardware directly — it only knows how to read and write numbers at addresses.

The bus matrix

The internal highway. It looks at the address the CPU is asking for and physically routes the request to the correct block — flash, RAM, or a peripheral.

Part 2

The memory map

This is the heart of LO1: how the chip's entire address space is carved up, and what lives where.

2.1  A 30-second hex refresher

Addresses are written in hexadecimal (base 16), flagged with a 0x prefix — for example 0x4002 1034. Hex exists purely for convenience: computers work in binary, but a 32-bit binary number is long and easy to misread, while its hex form is short and tidy.

Each hex digit represents exactly 4 bits (a nibble), so 8 hex digits represent all 32 bits of an address:

0x 4 0 0 2 1 0 3 4 0100 0000 0000 0010 0001 0000 0011 0100 ← 32 bits, one nibble at a time

With 32 bits, the number of unique addresses the CPU can reach is 232 = 4,294,967,296 — exactly 4 GB. That range runs from 0x0000 0000 up to 0xFFFF FFFF, and it's called the chip's address space. One more fact you'll use constantly: each individual address holds exactly one byte (8 bits).

2.5  So what does "programming a microcontroller" actually mean?

Underneath every library and abstraction, it comes down to one idea: writing numbers to specific addresses. Special hardware called the address decoder watches which address you're writing to and automatically routes your data to the right place — RAM, a GPIO pin, or an internal Arm feature. You never manually pick "RAM" or "GPIO"; the address itself decides.

Three raw examples from the lecture
// Setting a variable in RAM to 99 *((volatile uint32_t*)0x20000010) = 99; // Setting a pin in IOPORT (GPIO) high *((volatile uint32_t*)0x50000014) |= (1<<5); // Setting an ARM core peripheral high *((volatile uint32_t*)0xE000E010) |= 0x1;

If you've never seen C before, that first line looks like a small wall of punctuation. Let's take it apart piece by piece, because this exact pattern shows up constantly from here on:

PieceWhat it means
0x20000010The raw address we want to write to — a plain number.
(uint32_t*)"Treat that number as a pointer to a 32-bit unsigned integer." A pointer is just a variable whose value is an address, rather than an ordinary number.
volatileTells the compiler "don't get clever with this — hardware might change this value on its own, so read/write it for real, every single time, and don't cache or optimise it away." Essential for anything touching hardware registers.
*( ... )The dereference operator: "go to the address this pointer holds, and give me what's actually stored there" (or, for a write, "store this value there").
= 99Write the value 99 into that address.

The second example uses |= and << instead of a plain = — that's because registers are usually packed with many independent on/off switches (bits), and you want to flip just one without disturbing the others. We'll unpack bitwise operators properly in Part 4, once GPIO gives us a concrete reason to care.

The obvious question

The slides ask it directly: does that mean you need to memorise every single hex address on the chip? No. That's precisely what the reference manual (Part 3) and the CMSIS library (Part 7) exist to save you from.

Part 3

Using the reference manual

LO2 lives here: turning a 1,000-page PDF into the one address you actually need.

3.1  What is a reference manual?

Every microcontroller ships with a reference manual: an exhaustive, chip-specific document listing every peripheral, every register, its address, and exactly what each individual bit does. For the STM32C0 used in this course, that's RM0490 — and yes, it really is over a thousand pages. The lecture slide jokes that you "must memorise it all." You don't. Nobody does. You learn the lookup process once, and use the PDF's search and bookmarks every time after that.

3.2  Worked example: turning on the clock for GPIO

Digital circuits are built from logic gates that only move data on a rhythmic electrical pulse — think of it like a metronome keeping every gate in sync. That pulse comes from the RCC (Reset and Control Clock). GPIO pins are wired straight to the processor, but by default their clock is switched off to save power, so step zero for almost anything on this chip is: go enable the right clock in the RCC.

Here's the exact path the lecture walks through RM0490 to find that one bit:

  1. Find the address range. Table 7 (RM0490, pages 49–51) lists the address range for every bus and peripheral on the chip. RCC sits on the AHB bus, at 0x4002 1000–0x4002 13FF. That first number, 0x4002 1000, is RCC's base address.
  2. Find the specific register. Flip to RCC's own chapter (page 163) and open its register map — Table 31, on page 164. Scanning down for "enable GPIO clock" turns up a register called RCC_IOPENR, sitting at offset 0x34 from the base.
  3. Add them together. Register address = base address + offset = 0x4002 1000 + 0x34 = 0x4002 1034.
  4. Read the bit layout. The register map shows RCC_IOPENR's 32 bits. Five of them matter here — bit 0 through bit 4 enable the clock for GPIO ports A through F (skipping E, which this chip doesn't have): all default to 0 (off).
Bit01234
EnablesGPIOAGPIOBGPIOCGPIODGPIOF
// Enable clock for GPIOA (set bit 0 of RCC_IOPENR) *((volatile uint32_t*)0x40021034) |= (1<<0);
Interactive · address calculator

Base address + offset = register address

This is the calculation you'll repeat for literally every register on any Arm microcontroller. Try changing the offset to 0x00 — that's RCC_CR, the very first register in the RCC block.

3.3  The general recipe (works on any chip, any peripheral)

Strip away the RCC specifics and you're left with a four-step recipe that applies everywhere:

  1. Look up the peripheral's address range and register-map location in the manual's summary table (for RM0490, that's Table 7).
  2. Note its base address.
  3. Find the specific register you need — by name if you already know it, or by browsing the PDF's bookmarks if you don't — and read off its offset. Register address = Base + Offset.
  4. Check that register's bit layout to see which bits you can read or write, then set, clear, toggle or test exactly the bits you need.
Why this matters

Learn this recipe once and it transfers to every peripheral on every Arm Cortex-M chip you'll ever meet — not just GPIO, not just this course.

Part 4

GPIO registers

Now we apply the recipe to the pins you'll actually wire LEDs and buttons to.

4.1  What is GPIO?

GPIO stands for General Purpose Input/Output — the physical pins on the board where you connect real hardware: LEDs, buttons, sensors, motor drivers. They're wired directly to the processor, which keeps the delay between "code runs" and "voltage changes" as small as possible. The STM32C0 groups its pins into five ports: A, B, C, D, F.

Pins are named with the convention Pxy, meaning Port x, pin y. For example, PC13 means GPIO Port C, bit/pin 13. On the Nucleo board's user manual (UM2953, for the MB1717 reference board), you can trace every physical header pin back to its Pxy name.

4.2  The five registers that matter here

RM0490's GPIO chapter (Chapter 8, pages 178–195) applies identically to every port — the manual just writes GPIOx and lets x stand for A, B, C, D or F. Taking GPIO Port A's base address (0x5000 0000) and adding the offsets from that chapter gives:

RegisterOffsetAddress (Port A)Job
GPIOA_MODER0x000x5000 0000Sets each pin's overall mode
GPIOA_OTYPER0x040x5000 0004Output style: push-pull or open-drain
GPIOA_PUPDR0x0C0x5000 000CInternal pull-up/pull-down resistors
GPIOA_IDR0x100x5000 0010Read the current pin state (input)
GPIOA_ODR0x140x5000 0014Set the pin state (output)

Same base address, five different offsets — exactly the recipe from Part 3.

4.3  A quick bitwise-operator primer

Registers are 32 independent on/off switches packed into one number. To flip one switch without disturbing the other 31, C code leans on three operators. Try them below on a small 4-bit example before we scale up to a real 32-bit register:

OperatorUsed asEffect on a register
AND, &reg &= ~mask;Clears bits — anywhere the mask is 0, the result is forced to 0.
OR, |reg |= mask;Sets bits — anywhere the mask is 1, the result is forced to 1, others untouched.
NOT, ~~maskFlips every bit — turns "these are the bits I want" into "these are the bits I want to keep".
Left shift, <<1 << 5Slides a 1 into bit position 5, giving binary ...0010 0000. This is how you build a mask for "bit N" without counting zeros by hand.

The standard pattern for "set pin N's two-bit field to some value" is therefore always two lines: clear the field, then OR in the new value:

reg &= ~(0b11 << (N*2)); // clear both bits of the field first reg |= (value << (N*2)); // then set only the bits you want

4.4  GPIOx_MODER — choosing what a pin does

Each GPIO port has 16 pins, and MODER gives every single one of them 2 bits of its own — using up the full 32-bit register. The 2-bit value means one of four modes:

BitsModeWhat it does
00InputDefault for most pins. Reads a digital voltage in as a 0 or 1.
01General purpose outputLets code drive the pin's voltage — e.g. lighting an LED.
10Alternate functionHands the pin to a special peripheral — a timer, SPI, UART, etc.
11AnalogPuts the pin into analog-to-digital (ADC) mode to read a raw voltage level rather than just 0/1.

A real-world gotcha

On most STM32 boards, two pins — usually PA13 and PA14 — default to a special alternate-function mode that connects them to the onboard debugger (SWD). Switch those to plain GPIO and you can lose the ability to reprogram the board over USB. Worth knowing before you reach for "just set every pin to output."

4.5  GPIOx_OTYPER — how an output pin pushes voltage

OTYPER only matters for pins already in output mode, and it only needs 1 bit per pin (16 of the 32 bits are used).

BitModeBehaviour
0Push-pull (default)Actively drives the line to 3.3 V for a 1, and to 0 V for a 0. What you want for LEDs and most digital outputs.
1Open-drainPulls the line to 0 V for a 0, but simply disconnects (floats) for a 1 — you need an external pull-up resistor to actually reach 3.3 V. Required for shared buses like I2C.

In practice, you rarely touch this register — push-pull, the default, is what almost every project needs.

4.6  GPIOx_PUPDR — taming a floating input pin

Leave an input pin totally disconnected and its voltage drifts unpredictably — it "floats," randomly reading 0 or 1 from electrical noise. PUPDR switches on a tiny internal resistor to pin that voltage down firmly:

BitsSettingWhen you'd use it
00None (default)Fine when something external always drives the pin.
01Pull-upPin is pulled internally to 3.3 V. Perfect for a button wired to ground — the pin reads 1 (high) until the button is pressed and yanks it to 0.
10Pull-downPin is pulled internally to 0 V. For a button wired to the 3.3 V rail instead — reads 0 until pressed.

Once a pin's mode is configured, these are the registers your running code actually touches, over and over:

Part 5

Putting it all together

The running example throughout the lecture: an LED on pin PA5, and a pushbutton on pin PA4, wired through an internal pull-up.

The wiring means the pin reads high when the button is not pressed (pulled up to 3.3 V), and reads low the instant it's pressed (pulled down to ground). The example logic lights the LED whenever the pin reads high — so releasing the button turns the LED on, and pressing it turns the LED off. Try it:

And here is the complete raw-pointer program behind that behaviour, exactly as built up across the lecture:

int main(void){ *((volatile uint32_t*)0x40021034) |= (1<<0); // enable clock for GPIOA *((volatile uint32_t*)0x50000000) &= ~(0b11<<10); // clear pin 5's mode bits *((volatile uint32_t*)0x50000000) |= 0b01<<10; // pin 5 → output *((volatile uint32_t*)0x50000000) &= ~(0b11<<8); // pin 4 → input (redundant, it's the default) *((volatile uint32_t*)0x5000000C) |= 0b01<<8; // pin 4 → enable internal pull-up while(1){ uint32_t pin_state = (*((volatile uint32_t*)0x50000010)) & (1<<4); // read pin 4 if (pin_state != 0){ *((volatile uint32_t*)0x50000014) |= 1<<5; // pin 5 high } else{ *((volatile uint32_t*)0x50000014) &= ~(1<<5); // pin 5 low } } return 0; }

Notice every single line follows the same shape you've now seen four times: an address, a read or write, and a bit mask built from <<, |, & and ~. That repetition is the whole point — once the pattern clicks, every peripheral on the chip becomes approachable.

Part 7

CMSIS: making the code readable

Raw pointer arithmetic works, but it's easy to mistype an address and impossible to read back later. This is what CMSIS fixes.

7.1  What is CMSIS?

CMSIS (Cortex Microcontroller Software Interface Standard) is a hardware abstraction layer that Arm itself publishes for every Cortex-M chip. It takes every hex address and every bitfield from the reference manual and wraps them in named C structures, so instead of remembering 0x4002 1034 you write RCC->IOPENR.

To use it, you include the header file for your specific chip — for the STM32C031C6, that's #include "stm32c0xx.h" (downloaded from the STM32 GitHub repository). Every chip family has its own header, because every chip's addresses differ.

The same line, three ways
*((volatile uint32_t*)0x40021034) |= (1<<0); // raw address + raw bit RCC->IOPENR |= (1<<0); // named register, raw bit RCC->IOPENR |= RCC_IOPENR_GPIOAEN; // named register, named bit

All three lines do exactly the same thing to the exact same address. The third is the one you'll write in practice — it reads almost like a sentence, and a typo in a macro name fails to compile instead of silently writing to the wrong address.

7.2  Multi-bit fields need a small family of macros

A single on/off bit only needs one macro. But a 2-bit field like MODER's needs a small family, generated by the header for every pin:

// The least-significant bit of the pair #define PERIPHERAL_REGISTER_BITFIELD_Pos (LSB_of_bit_pair) // A mask covering both bits of the field #define PERIPHERAL_REGISTER_BITFIELD_Msk (0b11 << PERIPHERAL_REGISTER_BITFIELD_Pos) // Just the low bit of the pair set #define PERIPHERAL_REGISTER_BITFIELD_0 (0b01 << PERIPHERAL_REGISTER_BITFIELD_Pos) // Just the high bit of the pair set #define PERIPHERAL_REGISTER_BITFIELD_1 (0b10 << PERIPHERAL_REGISTER_BITFIELD_Pos)

Applied to pin 5's mode field, that becomes GPIO_MODER_MODE5_Msk, GPIO_MODER_MODE5_0 and GPIO_MODER_MODE5_1. To build any of the four 2-bit values, you clear the field with the mask, then OR in whichever of _0 / _1 you need:

Binary valueModeWhat you OR in
00Inputnothing — clearing the mask is enough
01OutputGPIO_MODER_MODE5_0
10Alternate functionGPIO_MODER_MODE5_1
11AnalogGPIO_MODER_MODE5_0 | GPIO_MODER_MODE5_1
GPIOA->MODER &= ~(GPIO_MODER_MODE5_Msk); // clear pin 5's field GPIOA->MODER |= GPIO_MODER_MODE5_0; // pin 5 → output // pin 5 → analog instead: GPIOA->MODER &= ~(GPIO_MODER_MODE5_Msk); GPIOA->MODER |= (GPIO_MODER_MODE5_0 | GPIO_MODER_MODE5_1);

7.3  The full example again, this time in CMSIS

Compare this to the raw-pointer version in Part 5 — same chip, same behaviour, same addresses under the hood:

int main(void){ RCC->IOPENR |= RCC_IOPENR_GPIOAEN; // enable clock for GPIOA GPIOA->MODER &= ~(GPIO_MODER_MODE5_Msk); GPIOA->MODER |= GPIO_MODER_MODE5_0; // pin 5 → output GPIOA->MODER &= ~(GPIO_MODER_MODE4_Msk); // pin 4 → input GPIOA->PUPDR |= GPIO_PUPDR_PUPD4_0; // pin 4 → pull-up while(1){ uint32_t pin_state = (GPIOA->IDR) & (GPIO_IDR_ID4); if (pin_state != 0){ GPIOA->ODR |= GPIO_ODR_OD5; // pin 5 high } else{ GPIOA->ODR &= ~(GPIO_ODR_OD5); // pin 5 low } } return 0; }
Reading tip

Notice LO3 in one glance: "using addressing, CMSIS and HAL." CMSIS is a hardware abstraction layer (that's the H, A and L) — it's the specific one Arm ships, sitting directly on top of the raw addressing you learned in Parts 2–5.

Summary

LO1 — Memory map

A 32-bit chip has a 4 GB address space split into boot space, flash, RAM, peripheral registers, and ARM core peripherals. Each address holds one byte, so subtracting addresses tells you sizes directly.

LO2 — Reference manual

Every register's address is base address + offset, both found in the manual's tables. Learn that lookup process once; it works for every peripheral, on every Cortex-M chip.

LO3 — GPIO in practice

MODER, OTYPER, PUPDR, IDR and ODR configure and drive a pin. Write it with raw pointers to see exactly what's happening, then write it with CMSIS because it's what you'll actually use.
