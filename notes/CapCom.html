Capture / Compare
& PWM, explained from zero

Every timer chip has a secret weapon hiding inside it: a little module called Capture/Compare. It's the thing that lets a microcontroller measure the exact moment something happens in the real world, and the thing that lets it generate perfectly-timed signals to control motors, LEDs and more. This is a from-scratch, no-assumptions walkthrough — built to be read by someone who has never seen a datasheet before, but who wants to understand it the way a third-year embedded systems student would.

Where we're headed

Learning outcomes

By the end of this lecture (and these notes) you should be able to do three things. Everything below is organised around getting you there.

LO1

LO2

Motivation

Why does a self-driving car need any of this?

Picture a self-driving car. It constantly has to answer three questions: when do I stop?, how fast am I going?, and which way do I turn? Every one of those questions comes down to the same two jobs, repeated thousands of times a second.

📥 Input Capture

Reading the physical world through sensors, and feeding that into the microcontroller. A LiDAR sensor, an ultrasonic sensor, a wheel encoder — all of these send pulses that the chip needs to time precisely.

📤 Output Compare

Controlling the physical world through actuators. Commands to steering motors, the accelerator, the brakes — all of these are signals the chip needs to generate at precise moments.

Capture/Compare (CapCom) is simply the name for the module living inside every hardware timer that does both of these jobs — precisely monitoring and precisely executing events — without needing the CPU to babysit it the whole time.

Big picture Everything in this lecture is really one idea wearing two hats. Capture = "tell me the timer's count when something happens outside." Compare = "do something outside when the timer's count reaches a value I chose." Same register, opposite direction of information flow.
LO1 · Part 1

Input Capture

Input Capture takes an instantaneous snapshot of the timer's current count (CNT) the moment a GPIO pin changes state. Crucially — it does not read a sensor value directly. It only ever reads time.

The stopwatch analogy Think of a stopwatch that's always running in the background — a "master clock" endlessly counting up. Input Capture is like pressing the lap button: the master clock never stops or resets, but the exact reading at the moment you pressed the button gets written down. That's exactly what happens electronically: the timer's CNT register keeps counting, and a pin transition (rising edge, falling edge, or either) causes the current CNT value to be copied into a capture register — instantly, in hardware, with no software delay.

Because the copy happens in hardware the moment the edge occurs, the CPU achieves precision event timing without ever needing a software delay loop or having to poll the pin over and over. Try it yourself below — the "timer" keeps free-running, and clicking the button simulates a real-world pin edge arriving at a random, unpredictable moment.

Two very different kinds of real-world events show up on that pin, and it matters which one you're dealing with:

Asynchronous (discrete) events

Unpredictable, one-off events from the physical world. A LiDAR (time-of-flight) sensor might detect a pedestrian 5 m away, then a car 20 m away, then a wall 100 m away — all at completely unpredictable times. Capture lets you grab the exact instant each of these arrives.

Periodic (continuous) events

Repetitive pulses from mechanical motion, e.g. a wheel encoder firing a pulse on every rotation. Here you capture consecutive timestamps ti and ti-1 and compute Δt = ti − ti-1 to work out a physical rate like speed or frequency — exactly how a self-driving car computes its current speed from wheel-encoder pulses.

LO1 · Part 2

Output Compare

Output Compare is Input Capture in reverse. Instead of the pin telling the timer something, the timer tells the pin something: when the free-running CNT reaches a target value that you've chosen and stored in the Compare register (CCR), hardware automatically changes the state of a GPIO pin — again, with zero CPU intervention at that instant.

Asynchronous use — a single future event

You want one precisely-timed action in the future. Example: a self-driving car's LiDAR suddenly detects an obstacle — brakes must engage, but to prevent the wheels locking up, a solenoid controlling the brake's hydraulic actuator needs a precise delay before it fires. Set CCR once, and the pin flips exactly on time.

Periodic use — a repeating signal

You want the pin toggling forever at a fixed rate — this is how continuous hardware signals (like PWM, later in this lecture) are created. Example: an ultrasonic parking sensor needs a constant square wave at a fixed frequency to drive its acoustic transducer.

CCR vs ARR — don't mix these up

A single timer can host multiple CapCom registers (up to 4 channels), each independent from the main auto-reload register (ARR):

  • Input Capture is driven purely by the timing of the physical pin — it has nothing to do with ARR.
  • Output Compare: the compare register (CCR) decides when within the cycle the pin changes state, while ARR decides how long the whole cycle is (i.e. the master timer's period/frequency).
Worked mini-example Think of a 60-second HIIT interval: 40 seconds of effort, 20 seconds of rest, repeating. That maps directly onto timer registers: ARR = 60 (the whole cycle resets every 60 "seconds"), CCR = 40 (the pin/state changes at the 40-mark). The timer keeps counting 0→60→0→60… forever; the compare event fires once per lap, always at count 40.
LO3 · Part 1

Pulse Width Modulation (PWM)

PWM is the single most common use of Output Compare. It's a pulse that resets at a specific, constant frequency — and microcontrollers can generate it entirely inside their timer hardware. It's used to control motor position/speed, dim LEDs, regulate voltage, and (later in this lecture) drive a servo.

Three terms define a PWM signal completely. Get comfortable with all three before moving on:

Frequency / Period

The timer counts from 0 up to a maximum value, then resets to 0. The time between resets is the period T [s]. Frequency is just its inverse: f = 1/T [Hz]. This is set to match whatever device you're driving.

Resolution

How many discrete steps the timer counts through in one period. With resolution index b, the counter has 2b steps, counting 0 to 2b−1. An 8-bit PWM signal counts 0→255 (256 steps) every period. Higher resolution = finer control of whatever's connected.

Duty Cycle (δ)

The fraction of the period that the output is high (th) before dropping low for the remainder: δ = th/T × 100%. Since PWM is digital, varying the duty cycle changes the average voltage the connected device sees — that's the whole trick.

Why this "fakes" an analog voltage A PWM pin is only ever fully HIGH (e.g. 3.3–5 V) or fully LOW (0 V) — never in between. But if it switches fast enough, the connected device (a motor, an LED, a filter circuit) effectively only "feels" the average voltage over time. A 25% duty cycle at 5 V averages to roughly 1.25 V; 75% averages to roughly 3.75 V. Change the duty cycle, and you change that average smoothly — a fully digital signal producing an effectively analog result.

LO3 · Part 2

Turning PWM into register values

A timer doesn't understand "500 Hz" or "25%" directly — it only understands three registers: PSC (prescaler), ARR (auto-reload) and CCR (compare). These two formulas are the bridge, and you'll use them constantly.

PWM frequency

fpwm = fclk / [(PSC+1)(ARR+1)]

Same update-frequency formula from the Timers lecture — PWM frequency is the timer's update frequency.

Duty cycle

δ = th/T × 100% = CCR / (ARR+1) × 100%

CCR is simply the fraction of the period you want the pin held high, expressed in timer ticks instead of seconds.

Worked example

1 kHz PWM, 25% duty cycle, 48 MHz clock

This is the exact example from the slides — walked through one line at a time. Use the calculator above (already loaded with these numbers) to follow along, or trace it by hand below.

Combine PSC and ARR into one unknown

We know fpwm = fclk / [(PSC+1)(ARR+1)], so rearranged:

// (PSC+1)(ARR+1) = fclk / fpwm
(PSC+1)(ARR+1) = 48,000,000 / 1,000 = 48,000

Apply the rule of thumb: scale the clock to 1 MHz

Rather than guessing how to split 48,000 between two unknowns, pick PSC+1 so the scaled timer frequency ftim = fclk/(PSC+1) becomes a clean 1 MHz:

PSC + 1 = fclk / ftim = 48,000,000 / 1,000,000 = 48
PSC = 47

Solve for ARR

ARR + 1 = 48,000 / (PSC+1) = 48,000 / 48 = 1,000
ARR = 999

Solve for CCR from the desired duty cycle

δ = CCR / (ARR+1) × 100%
CCR = δ × (ARR+1) / 100 = 25 × 1000 / 100 = 250

Sanity check

With the scaled timer running at 1 MHz, every tick is exactly 1 µs. ARR = 999 means the period is 1000 ticks = 1000 µs = 1 ms → 1 kHz. ✅ CCR = 250 means the pin is high for 250 of every 1000 ticks → 25%. ✅

LO2

Linking a GPIO pin to a timer

A GPIO pin doesn't automatically belong to a timer. Every pin can do several jobs (plain digital I/O, analog input, or one of several peripheral "alternate functions"), and you have to explicitly tell it which job to do. This is the wiring step that makes Capture/Compare physically possible.

Step 1 — GPIOx_MODER: choose the pin's mode

Every GPIO port has 16 pins, and each pin gets 2 configuration bits in the 32-bit Mode Register:

BitsModeMeaning
00Input modeDefault for most pins — reads a digital voltage in as 0 or 1.
01General purpose outputPin writes a voltage to connected hardware (e.g. lighting an LED).
10Alternate function modeHands the pin over to a peripheral — timer, SPI, UART, etc. This is the one CapCom needs.
11Analog modePuts the pin in A/D mode to read a raw analog voltage.
 
// Clear bits 10–11, then set Pin 5 of Port A to output mode
*((volatile uint32_t*)0x50000000) &= ~(0b11 << 10);
*((volatile uint32_t*)0x50000000) |= 0b01 << 10;

Notice the mask width always equals the number of bits you're clearing, shifted up to the LSB of the field you care about — the same pattern you used for every register in the Timers lecture.

Step 2 — which alternate function is "the timer"?

Setting 10 only says "alternate function mode" — it doesn't say which peripheral. Every pin on the STM32C031C6 supports several alternate functions (AF0–AF15+), documented per-pin in the datasheet's alternate function tables. A small excerpt for the pins used in this lecture:

Reading the real datasheet On the actual Nucleo board, this mapping lives in the User Manual (um2593, pin-out diagrams) and the Datasheet (DS_stm32C031C6, Tables 13–20 — one table per port). Every project starts the same way: figure out which physical pin you want to use, then look up which timer/channel/AF number it's tied to before writing a single line of code.

Step 3 — GPIOx_AFR: select that alternate function

The Alternate Function Register is split into two 32-bit halves, stored as an array AFR[2]:

  • AFR[0] — the "Low" register (AFRL), covers pins 0–7, 4 bits each
  • AFR[1] — the "High" register (AFRH), covers pins 8–15, 4 bits each
GPIOA->MODER |= 0b10<<14;    // Enable Alternate Function mode for PA7
GPIOA->AFR[0] |= 4 << 28;  // Set AF of PA7 to TIM14_CH1 (AF4)

GPIOC->MODER |= 0b10<<28;    // Enable Alternate Function mode for PC14
GPIOC->AFR[1] |= 11 << 24; // Set AF of PC14 to TIM3_CH2 (AF11)

Table 40 (RM0490, p.195) lists every AFR bit field — the pattern is always "4 bits per pin, pin number mod 8 tells you the shift, pin number ÷ 8 tells you which array element."

LO2 · Deep dive

The four CapCom registers

Once a pin is wired to a timer, four registers inside that timer do all the actual work. Every one of the STM32's general-purpose timers (like TIM3) has up to 4 independent channels, and each channel gets its own slice of these four registers.

CCMR — Capture/Compare Mode Register

Decides what kind of channel this is (input or output) and how it behaves. Split into CCMR1 (channels 1–2) and CCMR2 (channels 3–4), 8 bits per channel.

CCR — Capture/Compare Register

The actual number. In input mode, CNT gets written into here on an edge. In output/PWM mode, you write the target value here.

CCER — Capture/Compare Enable Register

The final switch that actually connects the channel to the physical GPIO pin, plus polarity (which edge / which active level).

DIER / SR — interrupt plumbing

DIER turns on interrupts per-channel; SR holds the flags that say an event actually happened.

CCMR — choosing input vs output (CCxS)

The bottom 2 bits of each channel's field in CCMR — called CCxS — decide everything:

CCxSMeaning
00Output Compare — this channel drives the pin.
01Input Capture, straight mapping — CCR1 reads timer input TI1, CCR2 reads TI2.
10Input Capture, cross mapping — CCR1 reads TI2, CCR2 reads TI1 (useful for advanced encoder configurations).

Reference: Table 87, p.515, RM0490. This same register also controls one-pulse mode — a single waveform of a specified width fired once in response to a single trigger, rather than repeating forever.

CCER — connecting the channel to the pin

Setting a mode in CCMR configures the channel's behaviour, but nothing reaches the physical pin until CCER says so:

  • CCxE — set high to actually enable/connect this channel to the pin.
  • CCxP — polarity bit. Meaning flips depending on direction:
DirectionCCxP = 0CCxP = 1
OutputActive → pin high, inactive → pin lowActive → pin low, inactive → pin high
InputTrigger (write CCR) on rising edgeTrigger (write CCR) on falling edge

DIER & SR — turning events into interrupts

Just like the update interrupt from the Timers lecture, CapCom events can trigger an ISR instead of being polled:

  • TIMx_DIER: set CCxIE for whichever channel(s) you want to raise an interrupt.
  • TIMx_SR: CCxIF is the flag that actually fired — meaning "rising/falling edge detected and CNT written into CCR" in input mode, or "CNT == CCR" in output/PWM mode.
  • CCxOF — the overcapture flag. If you're in input capture mode and a second edge arrives before you've cleared the previous CCxIF, this flag sets to warn you a value may have been overwritten before you read it.

Notice the symmetry Both directions touch exactly the same four registers (CCMR1, CCR1, CCER, DIER) — only the bit patterns differ. Once you've internalised one direction, the other is mostly a mirror image.
Detail that trips people up

Preload & glitch-free PWM updates

PWM is often changed while it's running — a servo sweeping, a motor accelerating. If you naively wrote a new CCR mid-cycle, you could get a visible glitch. Three settings fix this:

OCxPE — Output Compare preload enable
Set inside CCMRx. Ensures a new duty-cycle value only takes effect right after the counter resets, never mid-cycle — so a change is always applied cleanly at the start of the next period.
ARPE — Auto-reload preload enable
Set inside CR1. Same idea, but for frequency: a new ARR value only takes effect on a counter reset, not immediately.
UG — Update Generation
Set inside EGR. Manually forces (in software) an immediate transfer from the "preload" shadow registers into the active ones — done once, before you start the timer. Without it, the very first period runs with garbage/undefined prescaler and period values, producing a glitch on power-up.
Rule of thumb If you ever see a single wrong-looking pulse right when a PWM timer starts, it's almost always a missing UG bit. Set it once, immediately after configuration, before enabling the counter.
Case study 1

Driving a hobby servo motor

A standard hobby servo expects one pulse every T = 20 ms (a 50 Hz PWM signal). The width of that pulse — not its duty cycle percentage — tells the servo which angle to hold, anywhere from 0° to 180°.

The mapping used in this lecture: 0° → 500 µs pulse, 180° → 2500 µs pulse, linear in between:

th = t0 + [(t180 − t0) / 180] × θ  =  500 + (2000 / 180) × θ   [µs]

The reusable wrapper functions

Two small helper functions make the main code much cleaner: one to set any pin's alternate function generically, one to arm a channel into PWM Mode 1.

TIM3_PWM1_Init()
main() + ISR
void GPIO_SetAltFcn(GPIO_TypeDef *port, uint8_t pin, uint8_t num_af) {
  // AF register is an array of 2, 4 bits per pin: pins 0-7 -> AFR[0]; pins 8-15 -> AFR[1]
  uint8_t idx   = pin / 8;
  uint8_t shift = (pin % 8) * 4;   // 4 bits per register field

  port->AFR[idx] &= ~(0xF << shift);
  port->AFR[idx] |=  (num_af << shift);
}
void TIM3_PWM1_Init(uint8_t ch, uint32_t duty_us) {
  switch (ch) {
    case 1:
      // CC1S = 00 (Output), OC1M = 110 (PWM Mode 1)
      TIM3->CCMR1 &= ~(0b11<<0 | 0b111<<4);
      TIM3->CCMR1 |=  (0b110<<4) | (1<<3); // PWM1 + preload enable
      TIM3->CCR1  = duty_us;
      TIM3->CCER  |= (1<<0);
      break;
    // ...case 2, 3, 4 follow the identical pattern for CH2/CH3/CH4...
  }
  TIM3->EGR |= (1<<0);  // UG: apply preload values immediately
  TIM3->CR1 |= (1<<0);  // Make sure the timer is enabled
}
#define SERVO_MIN_US 500   // ~0 degrees
#define SERVO_MAX_US 2500  // ~180 degrees
volatile uint16_t pulse_width = SERVO_MIN_US;
volatile int16_t  step = 11;   // ~1 degree per update

int main(void) {
  Clock_Enable(GPIOA_BUS);
  Clock_Enable(TIM3_BUS);
  GPIO_InitPin(GPIOA, 6, ALT, NONE);
  GPIO_SetAltFcn(GPIOA, 6, 1);                    // PA6 -> AF1 -> TIM3_CH1
  Timer_Init(TIM3, TIM3_IRQn, 47, 19999, 1);   // 50 Hz update, interrupts on
  TIM3_PWM1_Init(1, 500);                       // start at 0 degrees
  while (1) { /* wait for interrupts */ }
}

void TIM3_IRQHandler(void) {
  if (TIM3->SR & (1<<0)) {           // UIF: fires every 20 ms
    TIM3->SR &= ~(1<<0);
    pulse_width += step;
    if (pulse_width >= SERVO_MAX_US || pulse_width <= SERVO_MIN_US) {
      step = -step;                        // reverse sweep direction
    }
    TIM3->CCR1 = pulse_width;              // new angle takes effect next period
  }
}

This ISR fires every 20 ms (once per PWM period) and nudges pulse_width a little each time, sweeping the servo smoothly back and forth — exactly the sweeping demo shown live in the lecture.

Case study 2

Pushbutton-controlled servo, with debounce

Second version of the demo: instead of auto-sweeping, pressing a pushbutton on PB11 steps the servo 45° at a time. That needs tΔ45 = (2000/180) × 45 = 500 µs per step — but real pushbuttons "bounce" (rapidly flicker) for a few milliseconds when pressed, so a second, faster timer (TIM16 at 1 kHz) is added purely to sample and clean up the button signal.

Why you need a second timer TIM3 is busy generating the 50 Hz servo PWM signal and can't also be used to sample a button every millisecond. TIM16 runs independently at 1 kHz just to drive the debounce logic — a nice example of a chip's multiple timers each doing one focused job.

The shift-register debounce trick

Every 1 ms, TIM16's ISR increments a counter. Every 10th tick (≈10 ms), it samples the pin and shifts that sample into an 8-bit history register, discarding the oldest bit. A press is only accepted once the register reads exactly 0x80 (0b10000000) — meaning "the seven most recent samples were all low, and nothing more recent has flickered back high yet." This ignores all the noisy bouncing and fires exactly once per real press.

The full debounce ISR

void TIM16_IRQHandler(void) {
  if (TIM16->SR & (1<<0)) {
    TIM16->SR &= ~(1<<0);
    static uint16_t debounce_timer = 0;
    static uint8_t  button_history = 0xFF;  // starts released (HIGH)
    debounce_timer++;

    if (debounce_timer >= 10) {           // sample every ~10 ms
      debounce_timer = 0;
      button_history = button_history << 1;      // make room for new sample, MSB discarded

      if (GPIO_InputReadPin(GPIOB, 11)) {
        button_history |= (1<<0);            // pin currently HIGH -> record a 1
      }

      // Detect a clean, stable falling edge -> pin went low when pressed
      if (button_history == 0x80) {
        pulse_width += step;
        if (pulse_width >= SERVO_MAX_US || pulse_width <= SERVO_MIN_US) {
          step = -step;
        }
        TIM3->CCR1 = pulse_width;         // latch new pulse width for next period
      }
    }
  }
}

Everything else — clock enables, GPIO_InitPin(GPIOB,11,INPUT,PULL_UP) for the button, and a second Timer_Init(TIM16, TIM16_IRQn, 47, 999, 1) call for the 1 kHz sampling timer — is set up in main() exactly like the earlier example, just with TIM3's own interrupt now turned off since it's only generating PWM, not driving logic.
